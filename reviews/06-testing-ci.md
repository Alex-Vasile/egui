# Review: testing, CI, and regression safety — hdr-egui-upstream.md
Reviewer focus: §7.7 QA story, §7.8 interaction list, CI feasibility per tier, test-program adequacy.
Checkout facts: Verified at tag `0.36.2` in this fork (which also still carries `crates/egui_glow`, `egui_plot`, `egui_web` — `git ls-tree 0.36.2 crates/`). egui_kittest delegates all rendering to `WgpuTestRenderer` (`0.36.2:crates/egui_kittest/src/wgpu.rs`); the external `kittest` 0.4.0 crate has no renderer of its own (registry `kittest-0.4.0/src/` = lib/query/state/node/filter only). CI (`0.36.2:.github/workflows/rust.yml`) runs `cargo test --all-features` **only** on `macos-latest` ("actual GPU"); Linux/Windows/wasm jobs are fmt/clippy/doc only.

## Findings

### 1. kittest-fp16-readback — kittest cannot snapshot fp16 today; §7.7's premise is false as written
- **Severity:** critical
- **Finding:** §7.7 claims "kittest/wgpu-offscreen can regression-test encoding correctness" because offscreen fp16 works headless. The offscreen *render* target is indeed `render_state.target_format` (`0.36.2:crates/egui_kittest/src/wgpu.rs`, texture created in `render()`), but the *readback* hardcodes 4 bytes/pixel: `texture_to_image` → `BufferDimensions::new` uses `size_of::<u32>()` and returns `image::RgbaImage` (u8) (`0.36.2:crates/egui_kittest/src/texture_to_image.rs`). On an `Rgba16Float` target the `copy_texture_to_buffer` bytes-per-row is half the required size → wgpu copy validation error → device poll/recv panic inside `texture_to_image`. There is no fp16 readback anywhere in egui_kittest or kittest 0.4.0. "Values >1.0 are just numbers" is true on the GPU; the number never survives to the test. Note the plan is internally inconsistent: §4 (`hdr-egui-upstream.md:137`) already admits capture "reads back Rgba8", while §7.7 assumes the harness can do it.
- **Evidence:** plan §7.7 (:442-447) vs `0.36.2:crates/egui_kittest/src/texture_to_image.rs` (BufferDimensions, `RgbaImage::from_raw`), `0.36.2:crates/egui_kittest/src/wgpu.rs` (`render()` target = `target_format`).
- **Suggested resolution:** Scope the fp16 readback as an explicit deliverable (it is currently only implied by the "capture fp16 readback" side-item, plan :213). The escape hatch already exists — `RenderState` fields are all `pub` and `WgpuTestRenderer::from_render_state` accepts a custom RenderState — so the gap is narrow: add a `texture_to_float_image` (Rgba16Float → f32 buffer) and either extend kittest's snapshot story or, simpler, write encoding tests as plain wgpu tests inside `egui-wgpu` using a hand-built fp16 `RenderState` (no kittest diff machinery needed at all).

### 2. contract-test-underspecified — "snapshot tests for the encoding contract" is not a spec
- **Severity:** major
- **Finding:** The plan never says what an encoding-contract test asserts. On u8 `RgbaImage` diffs (kittest's `SnapshotOptions::threshold` = max weighted squared YIQ distance, default 0.6, `0.36.2:crates/egui_kittest/src/snapshot.rs`) none of the interesting properties are even expressible. A real contract test on fp16 readback should assert numbers: (a) known linear input through `fs_main_gamma_framebuffer` reproduces `ecolor::gamma_from_linear` within fp16 quantization (±2⁻¹⁰ at 1.0, relative beyond); (b) values >1.0 survive upload→shader→blend (e.g. 2.0 and near-f16-max); (c) negatives behave per contract (they currently can't — see finding 4); (d) dithering disabled on float targets → bit-identical repeat renders; (e) SDR [0,1] output unchanged vs the u8 path within tolerance.
- **Evidence:** plan :447; `0.36.2:crates/egui_kittest/src/snapshot.rs` (threshold semantics, THRESHOLD_SWEEP — both u8-YIQ based).
- **Suggested resolution:** Add a short "encoding contract test matrix" subsection to §7.7 listing (input, expected output, tolerance, where it runs) per assertion above; state explicitly that these are float-readback assertions, not golden-image diffs.

### 3. u8-golden-blind — golden snapshots are structurally blind to the most likely HDR regressions
- **Severity:** major
- **Finding:** u8 storage clamps everything >1.0 to the same white: 2.0 and 10.0 produce identical goldens, and a regression that clamps HDR output to 1.0 will match a golden generated from the clamped pipeline perfectly. u8 goldens of HDR scenes can only guard SDR-appearance (chrome washout), not HDR values.
- **Evidence:** plan §7.7 "snapshot tests for the encoding contract"; readback is u8 by construction (finding 1); also kittest's screenshot flow reuses the same `RgbaImage` (`0.36.2:crates/egui_kittest/src/lib.rs:757-803`, `handle_screenshots`).
- **Suggested resolution:** Split the testing story into: (1) exact-value float-readback assertions for HDR values; (2) u8 goldens restricted to "SDR regions of an HDR scene look unchanged". Say explicitly that HDR-value changes are invisible to PNG goldens.

### 4. wgsl-negative-nan — the "odd-symmetric for negatives" contract is unimplemented in the shaders
- **Severity:** major
- **Finding:** §7.1 (:278) decides the float color contract is "odd-symmetric for negatives" and leans on "both WGSL entry points are already unclamped". Verified: CPU-side `ecolor::gamma_from_linear`/`linear_from_gamma` are odd-symmetric (`0.36.2:crates/ecolor/src/lib.rs`), but the WGSL twins have no negative branch — `gamma_from_linear_rgb`/`linear_from_gamma_rgb` compute `pow(x, …)` directly, and `pow(negative, x)` is NaN in WGSL (`0.36.2:crates/egui-wgpu/src/egui.wgsl:44-57`). A gamma-contract property test including negatives — exactly what this reviewer would propose — fails today.
- **Evidence:** plan :278 vs `egui.wgsl:44-57` at 0.36.2.
- **Suggested resolution:** Either drop odd-symmetry from the v1 contract (document "negatives are NaN, don't go there") or add sign handling to the WGSL fns and add the negative-value shader test to the tier-C/D test matrix. A CPU-only property test would green-light a contract the shader violates.

### 5. capture-silent-noop — capture on float surfaces fails silently, worse than §4 describes
- **Severity:** major
- **Finding:** §4 (:137) says capture "reads back Rgba8; float targets need a conversion step". Reality at 0.36.2: `CaptureState::read_screen_rgba` matches only `Rgba8Unorm`/`Bgra8Unorm` and otherwise does `log::error!` + early return — no panic, no fallback, the screenshot is simply never delivered to the awaiting channel (`0.36.2:crates/egui-wgpu/src/capture.rs`). `BufferPadding` also assumes 4 B/px. So on an HDR surface, `ViewportCommand::Screenshot` / `Frame::screenshot` degrade to a log line.
- **Evidence:** plan :137; `0.36.2:crates/egui-wgpu/src/capture.rs` (`_ =>` arm, `BufferPadding::new`).
- **Suggested resolution:** Sharpen §4's wording to the actual failure mode (silent no-op, not a clamp), and add to the tier-B deliverables: fp16 branch in `read_screen_rgba` (f16→f32→Color32/float) plus a loud error (or `Result`) instead of the early return.

### 6. decide-target-tautology — §7.4's invariant test is valuable only if fed synthetic `format_capabilities`
- **Severity:** major
- **Finding:** The §7.4 "invariant unit test: decide_target never returns an incoherent pair" (:403) is at tautology risk: a single canned case tests the decider against itself. Worse, in wgpu 30.0.1 the HDR-capable formats do **not** appear in `SurfaceCapabilities::formats` at all — that list contains only `Auto`-colorspace formats; `Rgba16Float` lives in `format_capabilities: Vec<SurfaceFormatCapabilities>` with per-format `color_spaces` (`wgpu-types-30.0.1/src/surface.rs:506-548`). Fixtures built from `formats` lists can never exercise the probe.
- **Evidence:** plan :403; wgpu-types-30.0.1 surface.rs (struct docs, `fn color_spaces(&self, format)` folds `format_capabilities`).
- **Suggested resolution:** Make it a property test over synthetic `SurfaceCapabilities` fixtures: Metal/EDR-like (`Rgba16Float` + `EXTENDED_SRGB` in `format_capabilities`), DXGI-like, float-without-EXTENDED_SRGB, empty caps. Assert: returned (format, color_space) is actually supported in caps; `HdrStatus` reason consistency with the choice; `preferred_color_space` totality on empty caps.

### 7. ci-single-os-backend — every GPU test runs on exactly one OS and one backend (Metal on M1)
- **Severity:** major
- **Finding:** rust.yml's `tests` job is `macos-latest` only; Linux does fmt/clippy/doc, Windows clippy-only, wasm check-only (`0.36.2:.github/workflows/rust.yml`). Consequences the plan ignores: all new GPU tests validate on a single backend (Metal, integrated M1, no HDR display, no window); Windows gets zero runtime verification anywhere in CI, so §7.3's "probe + SDR fallback path is exercised" (:339+) is macOS-only truth. Kittest deliberately prefers CPU adapters (lavapipe) where available (`0.36.2:crates/egui_kittest/src/wgpu.rs`), so developer machines and the CI runner exercise different adapters — fp16 math tolerances must be set with that in mind.
- **Evidence:** plan §7.7/§7.3; `0.36.2:.github/workflows/rust.yml` (job definitions).
- **Suggested resolution:** Add a sentence to §7.7 mapping each proposed test to its runner ("runs on macos-latest via Metal; Linux/Windows compile-only"), and set fp16 comparison tolerances (finding 2) so lavapipe-vs-Metal drift stays inside them.

### 8. manual-protocol-missing — "macOS tested, others experimental" has no documented protocol
- **Severity:** major
- **Finding:** §7.3 (:339+) commits to shipping with only macOS tested and "no hardware testing commitments before merge", but the only evidence offered is the author's app on one machine/display. Upstream reviewers will ask "how do I verify on my Windows HDR monitor / Wayland box?" and there is no answer in the plan: no checklist, no expected readings, no screenshot procedure, no definition of what "tested" means per platform. Without it, the "experimental" labels are unenforceable and the claim is anecdote.
- **Evidence:** plan :339-350; §7.9 (:455+) mentions up streaming the test app but not as a protocol.
- **Suggested resolution:** Commit to a MANUAL_TESTING.md (or example-app README) in PR 1: per-platform steps, deterministic test patterns, expected `HdrStatus`/headroom readings on EDR iMac / Pro Display XDR / Windows HDR monitor, and explicit "CI cannot validate this" disclaimers. Tie the upstreamed example to it (finding 14).

### 9. s78-interactions-incomplete — §7.8 list misses the harness itself, glow, wasm, and data-model fallout
- **Severity:** major
- **Finding:** The §7.8 list (:449-451) is wgpu-surface-centric. Missing, all verified at 0.36.2: (a) the kittest readback path (`texture_to_image`) — the harness is itself an interaction victim (finding 1); (b) `egui_glow` exists in this checkout (`git ls-tree 0.36.2 crates/`; eframe `glow` feature documented as live) — see finding 10; (c) wasm/web: kittest explicitly excludes `BROWSER_WEBGPU` ("we rely on blocking screenshots"), so the web path is compile-checked only (`check_wasm` job) — worth listing as "wasm must keep compiling with HDR types"; (d) multi-viewport × capture: `screen_capture_state: Option<CaptureState>` is a single shared state across viewports (`0.36.2:crates/egui-wgpu/src/winit.rs:35`) while viewports have per-window sizes — an interaction worth a test independent of HDR; (e) tier C/D data-model fallout: serde + `Eq` derives (finding 12); (f) `RendererOptions::default` has `dithering: true` — the dither-suppression interaction belongs in the §7.8 verify list, not just §2 prose.
- **Evidence:** plan :449-451; citations per item above.
- **Suggested resolution:** Extend the §7.8 list with (a)-(f), each marked CI-testable / manual-only (see finding 11's split).

### 10. glow-backend-matrix — "exactly one backend to fix" is false at this checkout and shapes the QA story wrong
- **Severity:** major
- **Finding:** The plan's header claim "egui_glow does not exist at 0.36 — wgpu is the only GPU backend" (:12-13) is contradicted by the repo: `crates/egui_glow` is a full crate at tag 0.36.2 and eframe ships a `glow` feature ("There is generally no need to enable both the `wgpu` and `glow` features"). Regardless of which resolution the plan takes (the tag may be fork-local rather than upstream's release), the QA consequences stand: kittest's `TestRenderer` trait has **only** a wgpu implementation, so glow rendering is untestable in CI even for SDR, and tier E's "every backend" (:190) silently excludes one. The plan must either prove glow is gone at the upstream target or name it as a second, CI-untestable backend.
- **Evidence:** plan :12-13, :190; `git ls-tree 0.36.2 crates/`; `0.36.2:crates/eframe/Cargo.toml` (glow feature); `0.36.2:crates/egui_kittest/src/renderer.rs` (only `WgpuTestRenderer` implements `TestRenderer`). [INFERENCE: upstream emilk/egui likely removed glow by its 0.36/0.37 — plausible but not verified from this checkout.]
- **Suggested resolution:** Add a §7.3-style verified footnote: `git -C upstream show <upstream-0.37-branch>:crates/` before PR 1; if glow survives, scope tier B/E test claims to wgpu explicitly.

### 11. surface-path-ci-gap — plan should say explicitly which of tier B is CI-validatable vs manual-only
- **Severity:** minor
- **Finding:** Headless CI cannot exercise: the real surface probe (`RenderState::create` headless falls back to `vec![Rgba8Unorm]` — `0.36.2:crates/egui-wgpu/src/lib.rs`, `surface_formats` `map_or_else`; kittest passes `compatible_surface: None`), `configure_surface` color-space threading, alpha-mode × fp16, `present_with_transaction` coexistence, `display_hdr_info` plumbing. To §7.4's credit, the "stored decision field, no derivation" design already minimizes the untestable surface — but the plan never states the split.
- **Evidence:** plan §7.7, §7.4; `0.36.2:crates/egui-wgpu/src/lib.rs` + `winit.rs`.
- **Suggested resolution:** One paragraph in §7.7: "CI validates the pure decider + offscreen pipeline; every windowed-surface behavior is manual-matrix only." Prevents false confidence and pre-empts reviewer questions.

### 12. tier-c-eq-serde — tier C's `ImageData::Float` cannot keep the `Eq` derive; serde tests are required, not optional
- **Severity:** minor
- **Finding:** `ImageData`/`ColorImage` derive `Clone, Default, PartialEq, Eq` at 0.36.2 (`0.36.2:crates/epaint/src/image.rs:14-16,46-47`). A `Float` variant over `Vec<[f32; 4]>` cannot derive `Eq` (f32), so adding it silently breaks the derive on `ImageData` and ripples into anything with `Eq` bounds. `ImageData` is also serde-derived behind a feature, so the new variant joins the serialization surface. `Rgba` sets the precedent: `PartialEq` only, serde via cfg_attr (`0.36.2:crates/ecolor/src/rgba.rs:8-12`).
- **Evidence:** plan §5 tier C, §7.1 derived API decisions; epaint/ecolor citations above.
- **Suggested resolution:** Add to the tier-C checklist: drop `Eq` (document it), serde roundtrip test for `ImageData::Float` including NaN/negative/>1.0 payloads, and note there is no existing fuzz corpus in-repo (none at 0.36.2), so serde roundtrips + property tests carry that weight.

### 13. tier-test-matrix — the per-tier deterministic tests that should exist (and which proposed ones are low-value)
- **Severity:** major
- **Finding:** The plan names exactly one test (§7.4's decide_target invariant) for three data-model tiers. Missing high-value tests: **Tier B** — `decide_target` property tests over synthetic caps (finding 6); `preferred_color_space` totality; `OutputEncoding` selection (`Rgba16Float` → gamma entry point); dither-suppression bit-exactness. **Tier C** — f32→f16 upload roundtrip rendered through the real shader and read back as floats (tolerance = f16 quantization); `Rgba16Float` MSAA render+resolve via kittest `with_render_options(msaa_samples: 4)` (§7.8's "MSAA resolve on fp16" is CI-testable this way — plan doesn't connect it); serde (finding 12). **Tier D** — `gamma_from_linear`∘`linear_from_gamma` ≈ id property incl. negatives (mirrors the WGSL gap, finding 4); exposure/stops slider monotonicity; serde of new types (`Rgba` precedent). **Tier E** — f16 vertex packing/unpacking roundtrip + bytemuck stride/alignment asserts + mesh serde. Tautological/low-value: a single-case decide_target test; runtime-asserting "HdrStatus mirrored in `frame.info()`" (not CI-able — needs a window; keep the field copy dumb); u8 goldens of HDR values (finding 3); raising `threshold`/`max_failed_pixels` to make u8 fp16-ish tests pass.
- **Evidence:** plan §7.4 (:403), §7.7, §5; kittest builder supports `with_render_options`/`renderer()` (`0.36.2:crates/egui_kittest/src/builder.rs`), and wgpu-types lists `Rgba16Float` in its multisample/filterable format arms (`wgpu-types-30.0.1/src/texture/format.rs:634,739,853`), so the MSAA test is feasible.
- **Suggested resolution:** Add a per-tier "tests" column/section to the ladder in §5 so each PR carries its own verifiable acceptance criteria.

### 14. example-ci-liability — the upstreamed test app is compile-only in CI; make it the manual protocol instead
- **Severity:** minor
- **Finding:** §7.9's "upstream our test app as an example" (:455+) costs less than feared — upstream examples are workspace crates compiled/clippy'd everywhere (rust.yml clippy `--all-targets` on Linux, `-p hello_world` on Windows, cargo-deny per-target, wasm clippy) but never run. The real liability is inverted: an example whose value only shows on HDR hardware cannot be visually validated by CI or by most maintainers, so it rots invisibly. Any golden PNGs it ships would also hit the PNG-in-LFS policy (`png_only_on_lfs.yml`) and the snapshot-update workflow commits with a PAT and never on main (`update_kittest_snapshots.yml`).
- **Evidence:** plan :455+; workflow files at 0.36.2.
- **Suggested resolution:** Ship the example snapshot-free, with a deterministic pattern menu + `HdrStatus` readout, and name it as the tool of the manual test protocol (finding 8). Accept compile-only CI coverage explicitly.

## Verdict
The plan's CI claim (§7.7) is its weakest verified section: the harness it names cannot read back fp16 today (finding 1), golden snapshots are blind to the regressions that matter (finding 3), and the shader side violates the decided negative-value contract (finding 4). The positive program is recoverable cheaply: float-readback value assertions + synthetic-caps property tests + an explicit CI-vs-manual split (findings 2, 6, 11) fit naturally into PR 1-3. "macOS tested, others experimental" is defensible only with a written manual protocol (finding 8) and a resolved glow answer (finding 10).
