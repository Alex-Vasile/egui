# Review: color science & rendering correctness — hdr-egui-upstream.md
Reviewer focus: §7.1 extended-gamma contract, §2 shader selection, and the numeric/colorimetric claims behind them.
Checkout facts: tag `0.36.2` = commit `49682f8` (2026-09-08, "Release 0.36.2 - Assorted fixes"), workspace version 0.36.2. `crates/egui_glow` IS a workspace member at this tag (root Cargo.toml:8, full painter + GLSL shaders, not a stub). Verified at tag: `egui.wgsl:44-56` gamma fns, `renderer.rs:409-428` entry selection + blend state, `ecolor/src/lib.rs:157-178`, `ecolor/src/color32.rs:8-12`, wgpu-types-30.0.1 `surface.rs:236-320`.

## Findings

### neg-contract-mismatch — §7.1 "odd-symmetric for negatives" contradicts the actual WGSL
- **Severity:** major
- **Finding:** The declared contract says negatives are odd-symmetric. ecolor's Rust fns *are* (`-f(-x)` mirror, ecolor lib.rs:159-163, 171-175), but the WGSL fns are **not**: `cutoff = rgb < 0.0031308` routes all negatives into the linear branch (`gamma_from_linear_rgb(-0.5) = -6.46`, vs odd-symmetric `-0.735`; egui.wgsl:52-56, and `linear_from_gamma_rgb` analogously ÷12.92, egui.wgsl:44-48). Both versions self-invert, so each is internally consistent, but the CPU picker (odd-symmetric encode) and the GPU decode (linear extension) disagree by 12.9× for any negative float texel/vertex color — exactly the values tiers C/E introduce. Separately, the WGSL computes `pow(negative, 1/2.4)` unconditionally in the discarded `higher` lane; WGSL `pow`/`log2` with negative base is undefined (implementation-defined, typically NaN via `exp2(y·log2 x)` in naga/Tint) — currently suppressed by `select`, one refactor (select→mix/arithmetic blend) away from NaN propagation.
- **Evidence:** plan §7.1 contract line + point 3 ("both WGSL entry points are already unclamped" — true for >1.0, silent on negatives); egui.wgsl:44-56; ecolor lib.rs:157-178; WGSL spec / webgpufundamentals fn reference ("Results are undefined if x < 0").
- **Suggested resolution:** Pick one negative extension and write it into the contract: either (a) linear extension (matches today's WGSL; then fix ecolor's odd-symmetric branch or document the divergence), or (b) odd-symmetric (then fix `gamma_from_linear_rgb`/`linear_from_gamma_rgb` to `sign(x)·f(|x|)` before any negative values can flow). Add sign-mirroring before `pow` regardless (kills the NaN lane), plus a CPU↔GPU round-trip test with negative inputs in the tier C PR.

### auto-colorspace-claim — §1/§2 "SDR-interpreted fp16 surface" misstates wgpu 30's `Auto` behavior
- **Severity:** major
- **Finding:** The plan says that leaving `color_space` untouched yields "an SDR-interpreted fp16 surface". wgpu 30.0.1 documents `Auto` as resolving to **`ExtendedSrgbLinear` (scRGB linear, EDR/HDR)** when the format is `Rgba16Float` and the surface supports it (surface.rs:244-258: "which fp16 surfaces have historically used"). So a smuggled fp16 surface on macOS is EDR-linear, and today's failure mode is gamma-encoded values interpreted as *linear* → washed-out mid-tones with broken headroom semantics — not SDR-interpreted clipping, and not the "black screen" of §1's #7484 story (that only occurs where fp16 isn't supported). The related §2 sub-claim "the heuristic can't distinguish [the two color spaces]" is correct, but "you'd get an SDR-interpreted fp16 surface" is factually wrong.
- **Evidence:** plan §1 ¶3, §2 ¶1; wgpu-types-30.0.1/src/surface.rs:242-258 (`Auto` doc), 285-306 (`ExtendedSrgbLinear` = scRGB, "Metal's extended dynamic range").
- **Suggested resolution:** Correct the §1 failure-mode paragraph against the `Auto` doc; note that `Auto`+fp16 already produces an EDR surface, which strengthens (not weakens) the case for an explicit policy (explicit beats accidental). Re-audit the §1 "naive knob-twiddling" example failures with this behavior.

### blending-premise-circular — §7.1 point 2's premise is verified true, but the conclusion rests on a misattributed rejection
- **Severity:** major
- **Finding:** Premise verified: egui composites with fixed-function blending in framebuffer space (`renderer.rs:415-428`: color One/OneMinusSrcAlpha-Add, alpha OneMinusDstAlpha/One-Add; no shader-side compositing), and float-texture bilinear filtering likewise runs on stored (gamma) values. So on an ExtendedSrgb surface, linear *storage* indeed buys nothing. But the reason given for rejecting the alternative — "ExtendedSrgbLinear … (SDR UI washout)" — is a property of the *wrong entry point* (gamma passthrough into a linear surface), which PR 2's explicit `OutputEncoding` fixes by definition. ExtendedSrgbLinear + the already-existing `fs_main_linear_framebuffer` is equally shader-correct today and gets *linear* blending and *linear* filtering for free. The plan also misses the strongest real argument for ExtendedSrgb that it never states: `ExtendedSrgbLinear` is **native-only** (surface.rs:299-301) — ExtendedSrgb is the only HDR choice that also covers web.
- **Evidence:** plan §7.1 point 2; §1 ("the policy encodes the one combination that is shader-correct today" — false: ExtendedSrgbLinear + linearize entry is a second correct combination); renderer.rs:409-414, 415-428; surface.rs:299-301.
- **Suggested resolution:** Rewrite point 2: ExtendedSrgb wins on (a) bit-exact status-quo parity for SDR chrome (zero AA/blend regression), (b) one texture grammar for u8 and float content, (c) web compatibility. State the residual permanent cost honestly: all HDR-over-HDR alpha compositing and filtering happens in gamma (e.g. 50%-alpha white over black composites to linear 0.214 instead of 0.25; 10%-alpha edges −90% in linear terms), fixed only by a future linear surface variant (which the scRGB policy path should anticipate).

### gamma-multiply-5pct — the "5.5% per multiply" number is not reproducible and is misattributed
- **Severity:** major
- **Finding:** I reproduced the composition error numerically with the real piecewise sRGB curve: multiplying two gamma-encoded factors gives **+37.7%** luminance error at enc-0.35 (linear 0.1) factors, **+1.5%** at mid-gray 0.5, **+0.1%** at 0.8, and is **exactly zero in the linear toe** (12.92·a × 12.92·b composes as a pure scale). No operating point yields 5.5%. The dominant error term is the **−0.055 y-intercept** (`(1.055a^γ−.055)(1.055b^γ−.055) − (1.055(ab)^γ−.055) ≈ −0.055·1.055(a^γ+b^γ)`), not the 1.055 slope; and "power laws compose correctly for large values so the error is bounded" has the direction backwards — a pure power law composes exactly at *all* levels, the affine terms break it everywhere, and the error shrinks toward white only because the curve is pinned at enc(1)=1. "Same class as the existing SDR dark-toe quirk" is worst precisely where the toe is *exact*.
- **Evidence:** plan §7.1 point 4; computed values above (reproducible in 5 lines of Python); ecolor lib.rs:157-178 constants.
- **Suggested resolution:** Replace the sentence with the measured shape ("level-dependent: exact in the linear toe, up to ~+38% luminance for dark-dark factor multiplies, →0 near white; accepted because it is bit-identical to today's SDR `in.color × tex` path") — or drop the quantification and argue parity with status quo, which is the argument that actually holds.

### fp16-precision-not-a-wash — "neither option wins on precision" is false as stated
- **Severity:** minor
- **Finding:** f16 has constant *stored-space* relative ULP (2⁻¹¹…2⁻¹⁰, 0.049–0.098%), but the display-relevant quantity is linear luminance, whose relative error is scaled by |d ln L/d ln V| = **2.4** in the power region. Gamma storage ⇒ up to ~0.234% luminance error vs ≤0.098% linear — linear is ~1.3 bits better where most content lives. Additionally gamma storage goes **subnormal** below encoded V = 2⁻¹⁴ (linear L ≈ 4.7×10⁻⁶), degrading the step to ~0.5% relative, while linear storage stays normal. Neither effect is perceptible (≪1% Weber JND), so the *decision* still rests on grammar — but the rationale "neither option wins" and "the classic argument is fixed-point-only" are both half-wrong: the redistribute-toward-shadows argument indeed needs fixed point, but the 2.4× derivative penalty and the denormal floor are real fp effects.
- **Evidence:** plan §7.1 point 5; f16 layout (10 explicit mantissa bits, min normal 2⁻¹⁴); computed values above.
- **Suggested resolution:** Restate as "linear is ~2.4× finer in relative luminance terms and avoids f16 subnormals below L≈5e-6; both are far below the ~1% visibility threshold, so precision does not decide". No decision change.

### sdr-by-construction-gotchas — §2 claim verified; two gotchas the plan underplays
- **Severity:** minor
- **Finding:** Verified end-to-end: `unpack_color` → [0,1] gamma (egui.wgsl), `fs_main_gamma_framebuffer` is a pure passthrough with no clamp (egui.wgsl:151-163), ExtendedSrgb = gamma-encoded extended range with 1.0 = SDR white (surface.rs:374-397). Alpha is consistent: Color32 is gamma-space **premultiplied** (color32.rs:8-12), blend is premultiplied (renderer.rs:419-426), and eframe prefers `CompositeAlphaMode::PreMultiplied` (winit.rs:266-284). Gotchas: (a) **dithering defaults to true** (`RendererOptions::default`, renderer.rs:228-233) and the field's own doc admits "Dithering assumes an sRGB output" (renderer.rs:193-196) — on an fp16 surface there is no 8-bit quantizer to hide the noise in, and near black the ±1/255 encoded noise maps to ×12.92 relative linear noise: pure shadow grain, not "meaningless". Every eframe app gets this without opting in once tier B lands. (b) Transparent-window compositing of an EDR layer (in what space the macOS compositor blends) remains unverified — correctly parked in §7.8 but should be listed as a §2 caveat since it can alter SDR appearance on the HDR path specifically.
- **Evidence:** plan §2 ¶3 ("no UI washout… by construction", "dither… is meaningless on fp16"); egui.wgsl:36-42, 151-163; renderer.rs:193-200, 228-233; winit.rs:266-284.
- **Suggested resolution:** Keep the by-construction claim but reword the dither item to "actively harmful in shadows on float targets"; PR 2 should flip the default for float targets and note the default-ON status quo. Add the compositor-space question to §7.8 explicitly for ExtendedSrgb (not just alpha mode).

### linearize-shader-not-precise — "precisely the correct shader for scRGB" is overstated
- **Severity:** minor
- **Finding:** Verified that `fs_main_linear_framebuffer` exists and does `linear_from_gamma_rgb(in.color × tex_gamma)` (egui.wgsl:134-148). Two imperfections: the dither is applied **before** linearization at 8-bit gamma granularity, so on a linear fp16 target the noise is distorted by the decode (×12.92 near black) instead of being shaped to the target's quantization; and negative texels (tier C) take the ÷12.92 branch, which contradicts an odd-symmetric contract (see neg-contract-mismatch). It is the right existing shader to select — "precise" oversells it.
- **Evidence:** plan §2 ¶2; egui.wgsl:134-148.
- **Suggested resolution:** Say "the correct existing entry point, modulo dither placement and negative handling"; fold both into the PR-2 scRGB policy work.

### premultiply-under-specified — "premultiplied (matching ColorImage storage)" is ambiguous in extended range
- **Severity:** major
- **Finding:** Color32 premultiplies the *gamma-encoded* u8 components (color32.rs:8-12); "matching" that convention means `stored = a × encoded_color`. For extended colors the alternative — premultiply in linear then encode (`enc(a·L)`) — gives different stored values for a<1, L>1, and only encoded-space premultiplication is consistent with the fixed-function `One, OneMinusSrcAlpha` blend in a gamma framebuffer. The DECIDED contract sentence doesn't say which; the two readings diverge for every semi-transparent HDR texel, and the WGSL `in.color × tex_gamma` multiply silently assumes one of them.
- **Evidence:** plan §7.1 contract line; color32.rs:8-12; renderer.rs:415-428; egui.wgsl:135-137.
- **Suggested resolution:** One sentence in §7.1: "premultiplication is applied to the gamma-encoded components (matching Color32/ColorImage), not linear-then-encode." Add a contract test: swatch at a=0.5, L=4 must composite as enc(4·0.5·…) per that rule.

### pq-100-nits-convention — 100 nits is not the current convention for PQ ingest
- **Severity:** minor
- **Finding:** §7.5 calls "nominal 100 nits the common convention" for mapping PQ/ST 2084 onto EDR. Industry practice moved to **203 nits** as the PQ reference white (ITU-R BT.2408, 2018, maintained through -8/2024; ST 2084's original ~100-nit diffuse white was revised to 203 in common use), and Apple's EDR mapping follows the 203-nit anchor. Mapping at 100 nits renders SDR-anchored PQ content ~2× brighter than the BT.2408 anchor.
- **Evidence:** plan §7.5 last bullet; ITU-R BT.2408; ACES community discussion of the 100→203 revision (acescentral.com).
- **Suggested resolution:** Default to 203 nits (BT.2408), document the choice and the macOS workaround nature of any constant; on Windows use `sdr_white_nits` exactly (the plan already passes through `DisplayHdrInfo`, so say so here).

### gamma-filtering-claims — §7.1 point 6's "perceptual interpolation, what pickers want" and unstated gamma filtering
- **Severity:** minor
- **Finding:** Two loose claims. (a) Hardware bilinear on the float textures filters *stored gamma* values (Rgba16Float is not an sRGB format), so tier C HDR images are downscaled/filtered in gamma — this shifts highlight energy (dark halos around bright content). It's inherited, consistent behavior with today's non-sRGB u8 textures, but it is a contract property the plan never states even though it constrains the future linear-surface variant. (b) "gradient strips interpolated in gamma = perceptual interpolation, what pickers want" — pickers interpolate in HSL/OkLab-like spaces, not raw gamma-RGB; gamma-RGB interpolation of saturated hues drifts in hue/saturation. It is only loosely better than linear for lightness between similar neighbors.
- **Evidence:** plan §7.1 point 6 ("Bonus:"); §7.1 point 3 (filtering path unchanged); egui.wgsl sample_texture; surface.rs:370-377 (non-*Srgb ⇒ values interpreted as encoded).
- **Suggested resolution:** Add "filtering and blending occur in gamma (stored space)" to the contract bullet list; soften the picker sentence to "closer to perceptual than linear for lightness; pickers needing hue-stable paths should interpolate in their own space before encode."

## Verdict
The §2 reading of the shader pipeline is accurate and well-anchored, and fixed-function gamma-space blending is real — the plan's biggest weakness is that §7.1's DECIDED rationale contains three quantitative/factual errors (5.5%, "precision is a wash", negative odd-symmetry) that upstream reviewers with color-science background will find in minutes, plus one wrong wgpu `Auto` claim underpinning tier B's framing. The ExtendedSrgb choice is still defensible — via status-quo parity and web-only support of encoded extended sRGB, an argument the plan inexplicably leaves out. Fix the rationale text and the negative-handling spec before drafting the upstream issue; none of the corrections flip the tier-B decision.
