# Review: upstream acceptance & maintainer politics — hdr-egui-upstream.md
Reviewer focus: would emilk/egui maintainers merge this, in this shape, in this order — and what has already changed upstream under the plan's feet.
Checkout facts: tag `0.36.2` verified locally: `crates/egui_glow` IS present (workspace member, opt-in `eframe/glow` feature, wgpu the default since 0.34 per `crates/eframe/CHANGELOG.md` entry #7615). Upstream state checked live 2026-10-24: open PR [#8703](https://github.com/emilk/egui/pull/8703) "egui-wgpu: add `SurfaceConfig::prefer_hdr` for HDR (scRGB) surfaces" (created 2026-10-12, BLOCKED, zero maintainer comments), issue #7484 open with no maintainer reply, issue #2712 open since 2023, issue #6863 open.

## Findings

### 1. stale-tracker-premise — Plan is blind to a live competing PR occupying tier B's exact API slot
- **Severity:** critical
- **Finding:** The plan's process section assumes a vacant upstream ("no open egui issue or PR requests HDR", checked 2026-09-11). As of 2026-10-12 that is false: PR #8703 by @JordyUSA adds `SurfaceConfig::prefer_hdr: bool` + `preferred_hdr_framebuffer_format()` to `egui-wgpu`, picks `Rgba16Float` + `EXTENDED_SRGB_LINEAR`, switches the fragment entry point for fp16 targets, fixes capture readback — i.e. it ships tier B with ~+200/−12 lines across exactly the files the plan names (lib.rs, winit.rs, renderer.rs, capture.rs). It is tested on real HDR hardware (Linux/Wayland, KWin, ramp to 4.0 verified brighter than SDR white), cites production use in LightCraft, and is currently merge-BLOCKED with only a CI-bot comment after 12 days. Opening the plan's PR 1 as specified, without referencing #8703, would be duplicate work by egui's own etiquette (CONTRIBUTING.md:30) and would likely be closed in favor of the earlier PR.
- **Evidence:** plan header + §7.9 ("no open egui issue or PR requests HDR", "target the 0.37 window"); PR #8703 (created 2026-10-12, files list, body); CONTRIBUTING.md:30 ("For bigger things, please file an issue first ... avoid having several people doing double work").
- **Suggested resolution:** Rewrite §7.9 strategy around #8703: review it now (the plan's shader/encoding analysis is exactly the review it needs — its `Auto`-color-space scRGB choice deserves the §2 double-gamma scrutiny), test it against the fork's app, and position the plan's `HdrPreference` policy enum + `HdrStatus` as a follow-up hardening PR that evolves the merged bool, not a competing first PR. Re-verify tracker status as a dated sentence before drafting any issue text.

### 2. glow-premise-false — "egui_glow does not exist at 0.36" is wrong and the "one backend" premise needs a written glow position
- **Severity:** critical
- **Finding:** The header claim "egui_glow does not exist at 0.36 — wgpu is the only GPU backend" is factually false at the cited tag: `crates/egui_glow` is a workspace member at 0.36.2 and an opt-in `eframe` feature (`crates/eframe/Cargo.toml:61`), actively maintained (0.36.2 glow fixes #8423, #8302). It was only demoted from *default* to opt-in in 0.34 (#7615, eframe CHANGELOG). So there are two live native backends, and a maintainer reviewer thinks in exactly those terms — Wumpf on wide-gamut color: "egui's rendering backends (each individually!) need to ..." (#2712 comment, 2024-10-23). The premise doesn't kill the plan (HDR lives entirely in egui-wgpu; glow apps simply stay SDR with zero breakage), but the plan currently draws its "scandalously cheap" conclusion from a false count, and any upstream issue that says "one backend" will be corrected in the first review comment.
- **Evidence:** `git show 0.36.2:Cargo.toml` (workspace members include `crates/egui_glow`); `git show 0.36.2:crates/eframe/Cargo.toml` lines 56-61 (`glow = ["dep:egui_glow", ...]`), defaults lines 28-36 (wgpu default); eframe CHANGELOG:80 (#7615 "Make `wgpu` the default renderer"); plan header + §1/tier B ("one backend to fix"); Wumpf quote in #2712.
- **Suggested resolution:** Correct the header. Add one explicit paragraph: `HdrPreference` is egui-wgpu-only; `egui_glow` remains SDR by design (OpenGL has no extended-sRGB swapchain concept), documented as such in the feature docs. That converts a review objection into a stated scope decision.

### 3. one-correct-combination-overclaim — "the one combination that is shader-correct" is false; the gamma-vs-linear fight must be argued on blending culture, not correctness
- **Severity:** major
- **Finding:** Plan §1 says the `PreferExtendedSrgb` policy "encodes the one combination that is shader-correct today." Its own appendix contradicts this: `fs_main_linear_framebuffer` (= `linear_from_gamma_rgb(color × tex)`) "is precisely the correct shader for scRGB", and PR #8703 demonstrates the other correct combination in the wild (Rgba16Float → linear entry point + `EXTENDED_SRGB_LINEAR`, "UI looks the same"). Two shader-correct configurations exist; they differ in blending space (fixed-function blending happens in surface space) and SDR semantics. The plan's §7.1 dismissal of linear ("SDR UI washout") conflates "linear content on a gamma surface" with "gamma input linearized by the correct shader," which is what #8703 does without reported washout. Ironically the plan's *gamma* choice is the culturally stronger one — egui deliberately blends in gamma ("egui prefers gamma color spaces for all blending", `crates/egui/src/lib.rs:147`; emilk's gamma-space filtering PR #7311 / #2071 lineage; Wumpf: egui "wants to do blending in a more perceptual space", #2712) — but the plan never makes that argument.
- **Evidence:** plan §1 last bullet of the "Why" paragraph, §2, §7.1 item 2, appendix egui.wgsl anchors; PR #8703 renderer.rs diff; `crates/egui/src/lib.rs:147`; Wumpf #2712 comment.
- **Suggested resolution:** Reframe §7.1's rationale: the pitch is *continuity* — extended-gamma surfaces preserve egui's existing gamma-blend grammar, u8 vertex semantics, and snapshot behavior bit-for-bit; scRGB-linear changes the blending space of every AA'd edge and stroke for all HDR users and diverges from egui's stated gamma preference. Drop "the one combination" phrasing entirely; a reviewer who knows #8703 will falsify it in one line.

### 4. api-shape-vs-8703 — §7.4's "deceiving variant" is the variant already shipped upstream; the in-place replacement risks becoming a rewrite of fresh API
- **Severity:** major
- **Finding:** §7.4 argues against keeping `preferred_framebuffer_format` beside a sibling as "the deceiving variant" — and PR #8703 ships precisely the sibling approach (`preferred_hdr_framebuffer_format(capabilities) -> Option<TextureFormat>` untouched next to the original). Two consequences. (a) If #8703 merges first, the plan's PR 1 in-place replacement `(caps, hdr) -> Result<(TextureFormat, HdrStatus), WgpuError>` is a breaking rewrite of a weeks-old public API — a near-unwinnable sell; the policy enum then has to arrive as an *evolution* (new `HdrPreference` consumed by a `decide_target`, old functions delegating or deprecated). (b) A detail error: the plan describes the current signature as taking `&SurfaceCapabilities` (§7.4) and callsites as `preferred_framebuffer_format(&caps.formats)` (§1), but at 0.36.2 it is `pub fn preferred_framebuffer_format(formats: &[TextureFormat]) -> Result<TextureFormat, WgpuError>` (`egui-wgpu/src/lib.rs:422-424`). The proposed change alters the input type, not just appends a parameter — meaning even a deprecation shim cannot be signature-compatible, which strengthens the "loud break" argument but must be stated accurately.
- **Evidence:** plan §7.4 "The *deceiving* variant is keeping the old function untouched beside a sibling"; PR #8703 lib.rs diff (new sibling fn, `prefer_hdr: bool`); `git show 0.36.2:crates/egui-wgpu/src/lib.rs:418-434`.
- **Suggested resolution:** Make §7.4 conditional on #8703's fate: if unmerged, propose the `decide_target` shape directly with a deprecation path for the 1-arg fn (one release); if merged, re-scope PR 1 as an additive evolution (`HdrPreference` enum + `HdrStatus`, existing fn delegating) and drop the in-place-replacement rationale. Fix the input-type description either way.

### 5. breaking-change-evidence — Conclusion right, evidence mostly wrong, and the documented deprecation-first preference is unaddressed
- **Severity:** major
- **Finding:** The plan justifies the in-place 0.x-minor break with "(0.35→0.36: wgpu major bump, glow removed, `Renderer::new` params → struct)". Verification: wgpu 30 bump — true (0.36.0, #8289). "glow removed" — false (see finding 2; not in the 0.36.0 changelog Removed section). "`Renderer::new` params → struct" — wrong release: `RendererOptions` was created in 0.33 (#7601), and `Renderer::new(device, format, options)` still takes it positionally at 0.36.2 (`renderer.rs:268-272`). Meanwhile CONTRIBUTING.md:92 states the actual policy: "each new egui release have some breaking changes, so we don't mind having a few ... if we can't [avoid them] we try to first deprecate old code using the `#[deprecated]` attribute" — and 0.36.0 did ship hard in-place removals (`Modifiers` off `RawInput`, `clip_rect_margin`) with no deprecation. So in-place breaks happen, but the plan's citation for the pattern is 2/3 fabricated-looking and it never engages the deprecation-first preference for a `pub fn` third parties call.
- **Evidence:** plan §7.4 parenthetical; `git show 0.36.2:CHANGELOG.md` (0.36.0 Removed section; wgpu 30 in egui-wgpu CHANGELOG 0.36.0); `git show 0.36.2:crates/egui-wgpu/src/renderer.rs:268-272`; eframe CHANGELOG:80; CONTRIBUTING.md:92; egui-wgpu CHANGELOG 0.33.0 (#7601).
- **Suggested resolution:** Replace the parenthetical with verified precedent (wgpu-30 bump; `Modifiers` removal in 0.36.0). Add a sentence answering the deprecation objection: e.g. deprecate the 1-arg fn for one release while `decide_target` lands, or argue why a `Result`-shaped replacement warrants a hard cut (semantic failure mode of the old signature under `Prefer`, per the plan's own argument).

### 6. pr1-scope-drift — PR 1 is described as "~150 lines, egui-wgpu only" but §7.4's reporting surface crosses into eframe
- **Severity:** major
- **Finding:** §1 sizes PR 1 at "~150 lines in `lib.rs` + `winit.rs`, no shader changes, no `epaint` changes," yet the "Suggested upstream sequencing" folds all of §7.4 into PR 1: `HdrStatus` mirrored into `frame.info()`, the in-place `preferred_framebuffer_format` replacement, `preferred_color_space`, and the `decide_target` refactor. `frame.info()` is eframe's `IntegrationInfo` (`crates/eframe/src/epi.rs:801`, struct at :1038-1040) — a different crate, published on the eframe cycle. That is a larger, cross-crate PR than the pitch admits, and cross-crate scope is exactly what slows egui reviews (contrast #8703, egui-wgpu-only, still unreviewed after 12 days; median first human reply 6 days, 41% of outside PRs get none within 14 — porchlamp.org/projects/emilk-egui).
- **Evidence:** plan §1 diff-size sentence; plan §5 PR 1 bullet ("plus the §7.4 API shape — `HdrStatus` reporting (`RenderState` + `frame.info()`), in-place ... replacement, symmetric `preferred_color_space`, single internal `decide_target`"); `crates/eframe/src/epi.rs:801,1038`; PR #8703 status.
- **Suggested resolution:** Split: PR 1a = egui-wgpu only (`HdrPreference`, probe, color-space threading, `RenderState::hdr_status`) — the #8703-comparable unit; PR 1b = eframe/epi `IntegrationInfo` pass-through. Present 1a first; 1b can ride the same release window without coupling the reviews.

### 7. capture-breakage-underweighted — enabling HDR silently breaks `capture`/screenshot; reviewers will demand the readback path in or beside PR 1
- **Severity:** major
- **Finding:** The plan lists "capture fp16 readback" as a side item (§5 item 5) and flags kittest capture in §4, but from a maintainer's seat this is not optional: turning on `HdrPreference` changes `RenderState::target_format` to `Rgba16Float`, which breaks `ViewportCommand::Screenshot`/`capture` readback for every user who opts in — #8703's author discovered the fp16 copy "fails wgpu validation" with 4-byte padding and had to write +105 lines of capture.rs (f16 decode, padding, clipping) plus unit tests to keep the feature non-broken. A PR that adds a documented-capability-breaking opt-in without shipping the readback fix invites a "please include the capture fix" round-trip.
- **Evidence:** plan §5 side items; plan §4 "Capture/kittest" bullet; PR #8703 body + capture.rs diff (+105 −5, `linear_f16_to_color32`, padding tests).
- **Suggested resolution:** Move fp16 capture readback into PR 1's acceptance criteria (or a hard-linked PR merged before/in the same release). Reuse #8703's approach (attribution costs nothing and shows good citizenship).

### 8. issue-anchors-missing — the ladder ignores existing upstream threads that anchor PR 2 and legitimize the demand case
- **Severity:** major
- **Finding:** PR 2 replaces the `is_srgb()` sniff with explicit `OutputEncoding` — but issue #6863 (open since 2025-04-26) already asks to "Get rid of 'Detected a linear (sRGBA aware) framebuffer' warning," with the body stating egui "can handle srgb render attachments perfectly fine, it just means you don't apply `linear_from_gamma_rgb`." PR 1's anchor is #7484 (open bug, reporter confirms "gamma applied twice ... fix has to be done on the egui side"). Neither is cited as a landing anchor; §7.9 only uses #7484 as a cautionary tale. Filing issues/PRs that reference these threads is both etiquette (CONTRIBUTING.md:23 "make sure there is not already a similar issue") and free evidence that the work fixes live bugs rather than adding speculative surface.
- **Evidence:** plan §7.9; issue #6863 body; issue #7484 (comment 2026-05-16); CONTRIBUTING.md:23,30.
- **Suggested resolution:** Map each PR to its anchor in the issue draft: PR 1 → #7484 (recreate semantics + the black-screen trap), PR 2 → #6863 (removes the warning, makes encoding explicit). Mention #8703 in both.

### 9. demand-case-inverted — the "nobody wants HDR" weakness is now the plan's strongest card, if played via #8703
- **Severity:** major
- **Finding:** The plan treats absent upstream demand as a passive risk. Since 2026-10-12 the demand argument is materially different: one external contributor shipped a working HDR PR, and one production product (LightCraft) is documented as running an earlier version of that change in the PR body — plus the plan author's own app as a second independent demand story. Two independent parties needing tier B is precisely the "ecosystem demand" emilk historically asks for (on wide-gamut: "Do you know anyone with a wide-gamut display that can help fix this? :)", #2712, 2023). The remaining acceptance risk is not demand but coordination: two parties proposing overlapping tier-B APIs.
- **Evidence:** plan header tracker-status; PR #8703 body (LightCraft link, Linux HDR test); emilk #2712 comment 2023-02-10.
- **Suggested resolution:** §7.9 should flip from "build the demand case" to "consolidate the demand case": engage on #8703, offer the fork's macOS verification (the PR is untested on macOS/Windows — the plan's EDR/headroom findings are directly useful review input), and fold the app in as a test case.

### 10. non-goals-hold — wide-gamut, web, and tone-mapping deferrals are culturally safe; say them as scope statements, not hopes
- **Severity:** minor
- **Finding:** The non-goals survive scrutiny. Wide gamut: #2712 has had "no movement" per Wumpf (2024) and none since on the general issue — a 3-year-stale feature issue is strong evidence maintainers won't block HDR on gamut. Web: Wumpf again — "Color is particularly cursed on WebGL, and nothing has been done yet." Tone mapping as app territory is uncontested in any visible thread. The plan already plans "one explicit sentence" for gamut (§7.2) — good; it should do the same for glow (finding 2) and for wasm (state that `SurfaceConfig` is native-only so web builds are untouched, pre-empting the eframe-web maintainers).
- **Evidence:** plan §5 non-goals, §7.2; Wumpf #2712 comment (both quotes); issue #2712 activity timeline.
- **Suggested resolution:** Keep the non-goals list; add the glow and wasm scope sentences; cite #2712's dormancy when justifying the gamut deferral.

### 11. issue-hook-order — lead with the bug and repro, keep the gamma analysis as the design differentiator
- **Severity:** minor
- **Finding:** §7.9 proposes leading the upstream issue with the shader-correctness analysis. Maintainers triage on user-visible breakage, not color science: #7484 (black screen, double gamma confirmed by reporter, open 14 months, no fix) is the hook; the ExtendedSrgb-vs-ExtendedSrgbLinear trap is the *second* section (why wgpu 30 + naive format selection burns people) and the *third* is the API that prevents both. The issue must also pre-empt the three predictable objections with one line each: scope ("egui-wgpu only, opt-in, glow/web unchanged"), maintenance ("~200 lines, invariant-tested `decide_target`, offscreen fp16 kittest snapshots per §7.7"), and CI-without-HDR-hardware ("encoding is testable headless; display interpretation is not; macOS verified manually by [us], Linux by #8703's author").
- **Evidence:** plan §7.9 bullet 1; §7.7; issue #7484 timeline; CONTRIBUTING.md:19-30 (issue/PR etiquette).
- **Suggested resolution:** Restructure the issue draft: (1) #7484-class failure + one-paragraph repro, (2) the encoding trap, (3) proposed `HdrPreference` surface + non-goals, (4) testing story. Attach the kittest offscreen-fp16 snapshot proof-of-concept.

### 12. hdrstatus-evolution-promise — "public signatures survive unchanged" is softer than it reads
- **Severity:** question
- **Finding:** §7.4 promises PR-2 evolution touches only `decide_target` while "both public signatures survive unchanged." Adding an scRGB policy variant later means a new `HdrPreference` variant — a 0.x-visible change to match behavior (and, if `HdrStatus`'s reason set grows, a non-exhaustive match hazard for downstream). That's culturally fine (egui breaks routinely), but the issue shouldn't oversell API stability; also confirm whether `HdrPreference`/`HdrStatus` should be `#[non_exhaustive]` from day one — egui uses that attribute sporadically, so match it to whatever neighboring egui-wgpu types do.
- **Evidence:** plan §7.4 "PR-2 evolution" bullet; `git show 0.36.2:crates/egui-wgpu/src/lib.rs` (check neighboring enum attributes for house style).
- **Suggested resolution:** One sentence in the issue: future color-space policies extend `HdrPreference` (optionally `#[non_exhaustive]`); drop the "survive unchanged" absolutism.

## Verdict
The plan's technical core (tiering, encoding analysis, extended-gamma contract) is genuinely upstreamable, and its gamma choice aligns with egui's documented gamma-blending house style (`egui/src/lib.rs:147`). But it was drafted against a vacuum that no longer exists: PR #8703 occupies tier B, is hardware-tested, and must be endorsed-or-evolved, not outrun. The egui_glow claim is false at the cited tag and must be corrected before any issue text ships. Best path: review + test #8703 from the fork, land the policy enum as its hardening follow-up anchored to #7484/#6863, split eframe reporting into a separate PR, and ship fp16 capture readback with the first PR.
