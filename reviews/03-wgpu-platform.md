# Review: wgpu 30 / platform matrix ground truth — hdr-egui-upstream.md
Reviewer focus: verify every wgpu- and platform-dependent claim against wgpu 30.0.1 sources and egui 0.36.2 tag.
Checkout facts: verified against `wgpu-types-30.0.1`, `wgpu-core-30.0.1`, `wgpu-hal-30.0.1`, `wgpu-30.0.1` in the cargo registry, and `git show 0.36.2:crates/...` in this repo. The plan's §1 probe shape `caps.color_spaces(Rgba16Float).contains(SurfaceColorSpaces::EXTENDED_SRGB)` **exists exactly as written** (`SurfaceCapabilities::color_spaces(&self, TextureFormat) -> SurfaceColorSpaces`, wgpu-types/src/surface.rs:537-549; `EXTENDED_SRGB = 1 << 5`, :481). §7.5 struct/field anchors (surface.rs:587-754) check out field-for-field. `Renderer::new` entry-point sniff, `configure_surface` field use, and the viewports-share-one-painter note are all accurate at 0.36.2. The DX12/Vulkan/Metal/GLES/web backend behavior below is read from capability code, not docs alone.

## Findings

### 1. dx12-no-extended-srgb — Windows HDR is impossible under PR 1's `PreferExtendedSrgb` policy, and the plan's `[INFERENCE]` is falsified
- **Severity:** critical
- **Finding:** §7.3 guesses wgpu 30's `ExtendedSrgb` on Windows "likely" maps to scRGB FP16. It does not: on DX12, `ExtendedSrgb` is **never reported and not mappable at all**. The DX12 adapter reports `Rgba16Float` → `EXTENDED_SRGB_LINEAR` only (scRGB, `DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709`), and `map_surface_color_space` hits `unreachable!("… never reported in the DX12 surface capabilities")` for `ExtendedSrgb`. scRGB-FP16 is wgpu's `ExtendedSrgbLinear`, a different variant with different shader semantics. Consequence: PR 1's probe deterministically fails on every Windows machine → permanent SDR fallback. "Windows labeled experimental — real-HDR output unverified" is the wrong label; the truth is "no HDR on Windows until the scRGB (ExtendedSrgbLinear) policy variant + `fs_main_linear_framebuffer` selection ship", i.e. the plan's PR 2. §7.3's enthusiasm ("Promising regardless: wgpu already surfaces Windows DXGI nits + chromaticity") conflates the data side (rich, real) with the presentation side (empty under this policy).
- **Evidence:** plan §7.3; wgpu-hal-30.0.1/src/dx12/adapter.rs:1313-1355 (fp16 → `EXTENDED_SRGB_LINEAR` only); dx12/mod.rs:1452-1466 (`unreachable!()` for `ExtendedSrgb`); wgpu-types-30.0.1/src/surface.rs:388-390 ("Not available on DX12, which has no encoded-extended-sRGB swapchain color space").
- **Suggested resolution:** Rewrite §7.3 from the wgpu source: per-backend table of `Rgba16Float` color spaces (Metal: `EXTENDED_SRGB|EXTENDED_SRGB_LINEAR|EXTENDED_DISPLAY_P3` unconditionally, metal/adapter.rs:409-415; DX12: `EXTENDED_SRGB_LINEAR` only; Vulkan: whatever `vkGetPhysicalDeviceSurfaceFormatsKHR` reports after `VK_EXT_swapchain_colorspace` is enabled; GLES: `SRGB` only, gles/adapter.rs:1345-1347; web: `EXTENDED_SRGB|EXTENDED_DISPLAY_P3` gated on fp16-canvas support alone). State explicitly that PR 1 ships HDR on macOS + web (+ rare Vulkan drivers), and that Windows/Linux HDR requires the PR 2 scRGB variant. Decide now whether `decide_target` should take a per-platform fallback (ExtendedSrgb → ExtendedSrgbLinear on DX12) in PR 2, since the §7.1 gamma contract and the `fs_main_linear_framebuffer` switch ride together.

### 2. egui-glow-exists — "egui_glow does not exist at 0.36" is factually false; the one-backend claim needs a different argument
- **Severity:** critical
- **Finding:** The header asserts "egui_glow does not exist at 0.36 — wgpu is the only GPU backend". `git ls-tree 0.36.2` shows `crates/egui_glow` present, and eframe 0.36.2 still ships a supported optional `glow` feature documented as the binary-size-saving alternative. Upstream reviewers will bounce an issue whose premise is false in the first paragraph. The defensible argument is capability-based and just as strong: the glow backend targets OpenGL/GLES, and wgpu's GLES backend reports `SurfaceColorSpaces::SRGB` only — no extended range exists in that stack, so HDR is wgpu-only by construction.
- **Evidence:** plan header; `git show 0.36.2:crates/egui_glow/Cargo.toml` (live package, version 0.36.2); eframe Cargo.toml:56-61 (`glow = ["dep:egui_glow", …]`, "no need to enable both"), :88 ("Switching from `wgpu (the default)` to `glow` can significantly reduce your binary size"); wgpu-hal-30.0.1/src/gles/adapter.rs:1345-1347 (SRGB-only color spaces).
- **Suggested resolution:** Replace the sentence with: "egui 0.36 has two backends; glow/OpenGL cannot express extended color spaces (GLES surfaces report sRGB only), so the HDR work is wgpu-only by capability, and eframe's glow path stays SDR." That survives review and pre-empts the "what about glow?" thread.

### 3. auto-is-not-sdr — §1's premise about `Auto` is wrong: wgpu 30 resolves `Auto`+fp16 to scRGB-linear, and egui's `get_default_config` spread would silently leak it in
- **Severity:** major
- **Finding:** §1 claims that with `color_space` untouched, "you'd get an SDR-interpreted fp16 surface". Wrong in the dangerous direction: wgpu 30's `Auto` resolves `Rgba16Float` to `ExtendedSrgbLinear` (historical scRGB behavior), falling back to `Srgb` only if linear is unsupported (resolve_auto_color_space). So an fp16 target with today's `configure_surface` is not "SDR-interpreted" — it is extended *linear*, which misinterprets egui's gamma-encoded output (washed/dark rendering) and silently activates extended range. This matters concretely because egui's `configure_surface` builds `SurfaceConfiguration` via `..surface.get_default_config(...)`, and wgpu's `get_default_config` sets `color_space: Auto` — the struct-update never touches it. If PR 1 plumbs the fp16 format but forgets the explicit `color_space` assignment, it ships exactly the #7484-class double-gamma bug the `HdrPreference` policy exists to prevent.
- **Evidence:** plan §1 ("SDR-interpreted fp16 surface"); wgpu-core-30.0.1/src/device/surface_config.rs:24-43 (`resolve_auto_color_space`: fp16 → `[ExtendedSrgbLinear, Srgb]`); wgpu-30.0.1/src/api/surface.rs:90-100 (`get_default_config` → `color_space: Auto`); egui 0.36.2 winit.rs:126-131 (`..get_default_config` spread, no color_space field).
- **Suggested resolution:** Fix the §1 narrative (the risk of the status quo is scRGB-linear misinterpretation, not SDR). Add to PR 1: `configure_surface` sets `color_space` explicitly from the stored decision (the plan already intends this — make it a named invariant), and extend the §7.4 unit test so `configure_surface`'s built `SurfaceConfiguration` is asserted coherent, not just `decide_target`'s return.

### 4. set-hdr-recreate-loses-textures — the §4 "full recreate" remedy is under-specified and would drop the font atlas and user TextureIds
- **Severity:** major
- **Finding:** §4 proposes "create-time-only plus an explicit `Painter::set_hdr()` that does the full recreate", leaning on "the safe recreate is context+state+renderer together". Neither half works as written. (a) Renderer-only recreate loses `Renderer.textures` (managed font textures, `ColorImage` uploads) and all `register_native_texture` bind groups — egui's TextureManager only sends *deltas* per frame, so after recreate, meshes reference TextureIds with no texture: "Missing texture" warnings and blank glyphs until the app happens to touch every texture. Re-pushing is *possible* (`Context::tex_manager()` exposes the manager) but re-registering user native textures has no recipe at all — `next_user_texture_id` restarts and app-held TextureIds dangle. (b) Recreating the egui Context is not implementable mid-run: apps hold `egui::Context` by value; there is no handle-swap story in eframe. So the only coherent runtime switch is: new RenderState + re-push all managed textures + documented invalidation of user texture handles — a much bigger API than §4 implies. This reinforces create-time-only as the actual PR 1 stance.
- **Evidence:** plan §4 ("push for create-time-only plus an explicit `Painter::set_hdr()` that does the full recreate"); egui 0.36.2 renderer.rs:251-253 (`textures: HashMap<TextureId, Texture>`, `next_user_texture_id`), :545-561 ("Missing texture" fallback), :755-767 (`free_texture`/`texture` accessors); context.rs:2417 (`Context::tex_manager()`); winit.rs delta-only texture updates in `paint_and_update_textures`.
- **Suggested resolution:** In §4, either (i) drop `Painter::set_hdr()` from the plan and declare format create-time-only in PR 1 (my recommendation; it matches upstream's appetite and the plan's own evidence), or (ii) spec `set_hdr()` fully: rebuild RenderState, re-push every texture from `ctx.tex_manager()`, return a new texture-id mapping for user textures, and note it is `unsafe`-adjacent for `register_native_texture` users. "Context+state+renderer together" should be deleted — it is not a deliverable.

### 5. headroom-is-per-viewport — the plan mirrors per-surface headroom into a global `frame.info()`, contradicting its own split
- **Severity:** major
- **Finding:** §7.4 correctly splits "format is global / headroom is per-surface", then decides the HdrStatus is "mirrored as a plain field in `frame.info()`" — but `Frame::info()` returns `IntegrationInfo`, a single global struct, while `display_hdr_info()` is queried per surface and differs across monitors (SDR + HDR windows is the exact multi-viewport case egui supports). A global field is wrong for anything except the primary viewport. The per-viewport data channel already exists and is the natural home: `ViewportInfo` is fed per viewport each frame (it already carries monitor/pixels-per-point context). Also correct in the plan: Metal's `display_hdr_info` is main-thread-only (returns `default` off-thread with a warn-once), so any refresh point must be the same main-thread path `configure_surface` runs on.
- **Evidence:** plan §7.4; eframe 0.36.2 epi.rs:748 (`Frame::info()` → `IntegrationInfo`); egui 0.36.2 viewport_info.rs:28 (`ViewportInfo`, per-viewport input each frame); wgpu-30.0.1/src/api/surface.rs:65-71 (`display_hdr_info(&self, adapter)`, re-queries per call, Metal main-thread-only); wgpu-hal-30.0.1/src/metal/surface.rs:55-89.
- **Suggested resolution:** Split the reporting decision: format/HdrStatus (global) in `RenderState` + `frame.info()`; headroom/`DisplayHdrInfo` (per viewport) in `ViewportInfo` or a per-viewport accessor. One sentence each in PR 1; add a kittest for the two-monitor SDR/HDR case only if cheap, otherwise document it.

### 6. probe-sees-first-surface-only — "which surface's probe decides" is not a free policy footnote; the code answers it today, and cross-viewport mismatch panics rather than falls back
- **Severity:** major
- **Finding:** §7.4 leaves "which surface's probe decides the global format (primary? any?)" as a residual footnote, but the 0.36.2 code already answers it: `RenderState::create` runs once, on the first `set_window`, with only that surface's capabilities (winit.rs:244-248). Later viewports inherit the global `target_format` and each surface is configured with it independently. If a later viewport's surface cannot configure (Rgba16Float, ExtendedSrgb) — plausible with Vulkan per-surface capabilities, exotic adapters, or headless-adjacent targets — `wgpu::Surface::configure` returns `()` and surfaces the failure as an uncaptured device error (default handler panics), **not** a recoverable `SurfaceErrorAction` from `on_surface_status`. So the fallback story is create-time-only by construction, and the footnote should record that.
- **Evidence:** plan §7.4 ("Residual policy footnote: which surface's probe decides"); egui 0.36.2 winit.rs:29 ("NOTE: all egui viewports share the same painter"), :241-248 (create on first window only), :122-139 (per-surface configure with shared format); wgpu-30.0.1/src/api/surface.rs:119-124 (`configure` returns `()`); wgpu-core-30.0.1/src/device/surface_config.rs:135-144 (UnsupportedColorSpace is a configure validation error, not a present error).
- **Suggested resolution:** State in PR 1: the probe input is the primary/first surface's caps; every viewport is configured from the same stored decision; per-viewport capability mismatch is a validation error by design (log + document), not a per-viewport fallback. If upstream wants per-viewport format freedom later, that is a different PR (it unpicks the shared-Renderer invariant).

### 7. headless-fp16-no-path — §7.7's offscreen fp16 regression story has no mechanism in egui-wgpu 0.36.2
- **Severity:** major
- **Finding:** §7.7 asserts headless offscreen fp16 rendering can regression-test encoding. True in principle, but the code cannot get there: `RenderState::create` with no compatible surface (exactly the kittest/offscreen case) substitutes `vec![Rgba8Unorm]` for capabilities (lib.rs:272-276), and kittest's default `WgpuSetup` passes `compatible_surface: None`, so `target_format` is always `Rgba8Unorm` and any HdrPreference probe silently no-ops. Nothing in the plan (not even the §7.4 `Option<TextureFormat>` escape hatch — which is described as a user escape hatch, not wired into the headless path) provides a forced-format test hook. As written, the plan's CI story cannot exercise the encoding contract it wants to protect.
- **Evidence:** plan §7.7; egui 0.36.2 lib.rs:272-280 (no-surface → `vec![Rgba8Unorm]`); egui_kittest 0.36.2 wgpu.rs:60-74 (`create_render_state` with `compatible_surface: None`), :96-100 (`RendererOptions::PREDICTABLE`, no format control).
- **Suggested resolution:** Add to PR 1 (or the §7.7 side-items): a test-only way to force `decide_target` output — e.g. `WgpuConfiguration::surface.hdr_preference` honored headlessly by extending the no-surface stub to consult `HdrPreference` and a `TestFormatOverride`. Wire one kittest snapshot that renders an >1.0 swatch on `Rgba16Float` and asserts the extended-gamma encoding.

### 8. capture-silent-empty — fp16 capture doesn't "lie", it silently produces nothing
- **Severity:** minor
- **Finding:** §4/§7.8 describe the capture issue as "snapshot tests of HDR swatches will lie". Actual behavior: `CaptureState` `to_rgba` matches only `Rgba8Unorm`/`Bgra8Unorm` and otherwise `log::error!(…)` + `return` — the readback completes with an empty/absent image (capture.rs:196-204). So on an HDR surface, `capture` feature degrades to silent capture failure, not wrong pixels. Worse for debugging than a lie (nothing fails visually), better than lying for tests (an empty capture is at least *detected*).
- **Evidence:** plan §4 ("float targets need a conversion step or snapshot tests … will lie"); egui 0.36.2 capture.rs:196-204 (`_ => log::error!` + return).
- **Suggested resolution:** Reword §4; add fp16→Rgba8 (with clamp/tonemap policy TBD) to the capture feature as a PR 1/2 checklist item, plus a debug_assert so the failure is loud in tests.

### 9. msaa-fp16-fine — MSAA resolve on fp16 is a verified non-issue on all realistic hardware
- **Severity:** minor
- **Finding:** §7.8 lists "MSAA resolve on fp16" as an open verify item. wgpu's Metal backend grants `MULTISAMPLE_RESOLVE` to `Rgba16Float` except on `apple1x` GPUs (metal/adapter.rs:189-194); Apple-silicon Macs are far past that generation [INFERENCE: `apple1x` = first-gen Apple GPU family]. DX12's `R16G16B16A16_FLOAT` is a mandatory FL11 format with standard MSAA [INFERENCE: D3D11 functional spec, not in wgpu source]. egui's MSAA intermediate target just uses `render_state.target_format`, so no change is needed. This item can be closed rather than carried.
- **Evidence:** plan §7.8; wgpu-hal-30.0.1/src/metal/adapter.rs:186-194; egui 0.36.2 winit.rs (`resize_and_generate_depth_texture_view_and_msaa_view` builds the intermediate target from `target_format`).
- **Suggested resolution:** Replace the open item with the resolved statement + the `apple1x` caveat for iOS-tier hardware.

### 10. jitter-fix-stale — `present_with_transaction` coexistence concern is mostly stale; the fix in 0.36.2 is a latency clamp
- **Severity:** minor
- **Finding:** §7.8 asks to verify "`present_with_transaction` macOS resize fix coexistence". At 0.36.2 the jitter fix is a cargo feature that (a) bumps `desired_maximum_frame_latency` to ≥2 during live resize (winit.rs:104-110) and (b) requires/presumes CAMetalLayer `presentsWithTransaction` (Cargo.toml:54, winit.rs:423). Neither touches `SurfaceConfiguration::color_space`; reconfigure during resize rebuilds from the stored decision, so HDR state survives. No code-level interaction exists. Residual hardware risk (transaction present + extended-range drawable) is untestable here and belongs in the macOS hardware pass, not the design.
- **Evidence:** plan §7.8; egui 0.36.2 winit.rs:104-110, :423; Cargo.toml:54.
- **Suggested resolution:** Downgrade to a manual-QA checkbox on macOS ("enable jitter-fix + HDR, drag-resize"), and note the reconfigure path preserves color space by construction.

### 11. transparency-no-conflict — nothing in wgpu 30 makes Rgba16Float + ExtendedSrgb + transparency invalid; alpha and color space are validated independently
- **Severity:** minor
- **Finding:** Answering the plan's open question: `validate_surface_configuration` checks color space against per-format caps and alpha mode against caps in two independent blocks — no cross-constraint exists. Metal reports exactly `[Opaque, PostMultiplied]` alpha modes; egui's transparent path picks `PostMultiplied` (Metal has no `PreMultiplied`), which composes fine with extended-range values at the validation level. The only platform where the combo breaks is DX12 — because `ExtendedSrgb` doesn't exist there at all (finding 1), independent of alpha. Actual compositor behavior with premultiplied >1.0 content remains untestable without hardware [INFERENCE: fine on macOS; CAMetalLayer color-matches regardless of display, per metal/adapter.rs:385-388].
- **Evidence:** wgpu-core-30.0.1/src/device/surface_config.rs:135-172; wgpu-hal-30.0.1/src/metal/adapter.rs:468-471; egui 0.36.2 winit.rs:266-290 (`install_surface` alpha selection).
- **Suggested resolution:** Close the §7.8 "transparent windows (alpha mode × HDR)" item with the above; keep a single macOS manual-QA checkbox for compositor behavior.

### 12. hdr-info-platform-nits — §7.5 is broadly right but misstates iOS headroom and omits the `tone_map_headroom` SDR-flag step
- **Severity:** minor
- **Finding:** Three corrections to the otherwise-verified §7.5: (a) `DisplayHeadroom` is "Populated only on macOS; `None` on iOS, tvOS, and visionOS" (wgpu-types surface.rs:645-649) — the plan's "maps to the NSScreen/UIScreen EDR properties" implies iOS coverage it doesn't have. (b) `tone_map_headroom()` precedence has four steps, not three: Apple → **`Some(1.0)` when `coarse.high_dynamic_range == Some(false)`** → `max_nits / sdr_white_nits` → `None`; the middle step prevents Windows SDR outputs from surfacing "phantom headroom" and matters for the plan's HdrStatus design (an SDR Windows display reports `Some(1.0)`, not `None` — apps should treat 1.0 as "no headroom", not as a probe failure). (c) `DisplayGamut` is `#[non_exhaustive]` and explicitly unordered — fine as pass-through data, but any egui-side ordering/matching would be a forward-compat hazard.
- **Evidence:** plan §7.5 and appendix; wgpu-types-30.0.1/src/surface.rs:645-660, 712-757, 703-710.
- **Suggested resolution:** Patch §7.5's bullet list with (a) and (b); add one sentence to the HdrStatus design: `tone_map_headroom() == Some(1.0)` is a valid steady state, `None` is the "unknown" state.

### 13. web-deferral-stale — the web deferral rationale ("until wgpu's web surface color spaces settle") is outdated: wgpu 30's web backend already reports `EXTENDED_SRGB` for fp16 canvases
- **Severity:** question
- **Finding:** §5 lists "web/wasm until wgpu's web surface color spaces settle" as a non-goal. In wgpu 30, the browser WebGPU backend advertises `EXTENDED_SRGB | EXTENDED_DISPLAY_P3` on `Rgba16Float`, "gated on fp16-canvas support alone — not on whether the display is currently HDR" (webgpu.rs:4143-4166), and the docs direct web users to request `ExtendedSrgb` explicitly for HDR canvas output. The color-space side has settled; what remains un-settled is egui-side plumbing (eframe web wiring, fp16 canvas request, and whether `ExtendedSrgbLinear` is native-only — it is). The deferral may still be right (scope), but the stated reason is wrong and will be corrected in review.
- **Evidence:** plan §5 ("web/wasm until wgpu's web surface color spaces settle"); wgpu-30.0.1/src/backend/webgpu.rs:4143-4166; wgpu-types-30.0.1/src/surface.rs:379-390 (web notes for ExtendedSrgb/ExtendedSrgbLinear).
- **Suggested resolution:** Reframe the non-goal as "web deferred for scope/egui-plumbing reasons; wgpu 30 already supports the encoded-extended canvas path" — or, if the probe-then-fallback architecture is format-agnostic, note web comes nearly free and might graduate to a stretch goal.

### 14. wayland-no-cm — wgpu 30 has no Wayland-native color management; Linux HDR is purely the Vulkan extension path, and the probe will usually fail it
- **Severity:** minor
- **Finding:** §7.3 asks about "color-management protocol maturity" as if wgpu participates in it. It does not: there is no wp_color_management/frog/xx-color code anywhere in wgpu-hal/core 30; the entire Linux story is `VK_EXT_swapchain_colorspace` (requested unconditionally as a Vulkan instance extension, instance.rs:280-282) feeding `vkGetPhysicalDeviceSurfaceFormatsKHR` results straight into the reported caps. That means Linux HDR support under the plan's policy reduces to: does the driver expose `VK_COLOR_SPACE_EXTENDED_SRGB_NONLINEAR_EXT`? In practice essentially no desktop driver does (the spec has required only SRGB_NONLINEAR since forever; EXTENDED_SRGB_LINEAR is what NVIDIA-class drivers expose) [INFERENCE from driver ecosystem knowledge, not from wgpu source]. So on Linux the probe fails → SDR fallback, deterministically-ish — the "probe succeeds but output is wrong" footgun the parent asked about does not apply to PR 1's policy on Linux; it applies only to PR 2's ExtendedSrgbLinear-on-Wayland case, where the compositor can honor scRGB without an active HDR mode and produce wrong-brightness output.
- **Evidence:** plan §7.3 (Linux/Wayland bullets); wgpu-hal-30.0.1/src/vulkan/instance.rs:280-282; vulkan/swapchain/native.rs:150-163 (caps straight from `vkGetPhysicalDeviceSurfaceFormatsKHR`); conv.rs:187-202 (variant mapping); absence of any Wayland color-management protocol code in wgpu-hal-30.0.1.
- **Suggested resolution:** Rewrite the Linux bullet: "wgpu 30 exposes Vulkan swapchain color spaces only; no Wayland color-management protocol support. `EXTENDED_SRGB` is driver-rare, so Linux is probe-gated SDR in practice. PR 2's scRGB path is where the probe-succeeds-but-wrong-output risk actually lives (compositor-dependent), and should carry the experimental label then."

## Verdict
The plan's egui-side anchors and API-shape decisions are solidly grounded — the probe expression, Renderer pipeline coupling, shared-painter invariant, and §7.5 data structures all verify against source. The two credibility-breaking errors are both at the platform layer: the DX12 `ExtendedSrgb` absence (which silently converts the Windows story from "experimental HDR" to "no HDR until PR 2") and the false "egui_glow does not exist" premise. The `Auto`→scRGB-linear correction, the set_hdr texture-loss hazard, and the headless-fp16 test gap are the substantive design fixes to make before drafting the upstream issue. With findings 1, 2, 3, 4, 5, 6, and 7 incorporated, the wgpu/platform content of the plan would be source-accurate end to end.
