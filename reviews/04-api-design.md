# Review: API design & Rust API guidelines — hdr-egui-upstream.md
Reviewer focus: the proposed public API surfaces — `HdrPreference`, `HdrStatus`, the format/color-space function split, `OutputEncoding`, and the tier C/D/E type sketches.
Checkout facts: verified against `git show 0.36.2:` in `/Users/alex/Developer/egui` (fork tags jump 0.34.3 → 0.36.2; no 0.35 tag exists here) and `wgpu-types-30.0.1` in the cargo registry. `crates/egui_glow` exists and is a supported eframe backend at 0.36.2 (eframe `glow` feature, `glow_integration.rs`, workspace glow 0.17). `preferred_framebuffer_format` already returns `Result<TextureFormat, WgpuError>` at this tag.

## Findings

### 1. hdr-status-payload — `HdrStatus` payload unspecified; §1 and §7.4 contradict each other
- **Severity:** critical
- **Finding:** §7.4 writes the enum as `Hdr { .. }` — the payload is blank, so PR 1 literally cannot be written from the plan. Worse, §1 says `RenderState` records "`hdr_active: bool`" while §7.4 (later, but unmarked as superseding) says `RenderState` "holds the authoritative `HdrStatus` — an enum, not a bool". Two different fields for the same concept in the same struct.
- **Evidence:** plan §1 ("records what it got (`RenderState::hdr_active: bool`)") vs §7.4 ("an enum, not a bool"); tag `egui-wgpu/src/lib.rs:105-140` shows the current `RenderState` field list.
- **Suggested resolution:** delete the §1 `hdr_active: bool` sentence, and pin the payload, e.g. `Hdr { format: TextureFormat, color_space: SurfaceColorSpace }` (mirrors `decide_target`'s outputs, so bug reports are self-describing) with `Sdr { reason: SdrReason }` and a `SdrReason` enum rather than an open `reason` blob. Derive `Clone, Copy, Debug, PartialEq, Eq` — nothing here needs more.

### 2. hdr-refresh-nonexistent — "refreshed at reconfigure" has no code path; the frame.info() mirror duplicates an existing accessor
- **Severity:** critical
- **Finding:** §7.4's central reporting claim — `HdrStatus` "refreshed at reconfigure/recreate (the same points `configure_surface` runs)" — does not match the code. `configure_surface` runs on every resize/`Outdated` (winit.rs:96-139, :526-533, :590, :612) and re-probes nothing: `RenderState::create` runs exactly once, guarded by `if self.render_state.is_none()` (winit.rs:245-249). The app-visible `RenderState` is a one-shot clone taken at `painter.render_state()` (eframe `native/wgpu_integration.rs:263`). So either HdrStatus is create-time-immutable (then "refreshed" is false and the mirror is pointless), or the plan needs a Painter→eframe publish path that does not exist and is not sketched. Additionally, `Frame::wgpu_render_state() -> Option<&RenderState>` already exists (epi.rs:802-806) — a mirrored plain field in `IntegrationInfo` would be a *third* copy (Painter's, Frame's clone, the mirror) with three staleness stories.
- **Evidence:** plan §7.4; tag `crates/egui-wgpu/src/winit.rs:245-249, :526-533`; tag `crates/eframe/src/native/wgpu_integration.rs:263`; tag `crates/eframe/src/epi.rs:802-806`.
- **Suggested resolution:** for PR 1, declare HdrStatus create-time-immutable, document that, and skip the mirror entirely — `frame.wgpu_render_state().map(|rs| rs.hdr_status)` already answers the question. If a mirror is kept, specify who writes it per frame (the eframe glue that already refreshes `cpu_usage`, IntegrationInfo at epi.rs:897-911) and what happens to the stale `Frame` clone after a future `set_hdr()` recreate. Also document the lifetime asymmetry the plan glosses: HdrStatus is global (shared `RenderState`), while the `DisplayHdrInfo` side-item is per-surface/per-viewport — both landing in `frame.info()` with different lifetimes needs one explicit sentence.

### 3. glow-type-home — the plan's "exactly one backend" premise is false, and HdrStatus's type home / feature gating is undecided
- **Severity:** major
- **Finding:** egui_glow exists at 0.36.2 with an active Cargo.toml and no deprecation notice; eframe documents glow as a supported renderer ("Switching from `wgpu (the default)` to `glow` can significantly reduce your binary size", eframe Cargo.toml:97-101). The header claim "wgpu is the only GPU backend, so there is exactly one backend to fix" is wrong for this tag, and every shared-surface API decision inherits the question the plan never asks: where do wgpu-typed things (`HdrStatus`, `DisplayHdrInfo`) live in backend-neutral API? `IntegrationInfo`/`Frame` gate every wgpu member behind `#[cfg(feature = "wgpu_no_default_features")]` (epi.rs:83-84, :679-680, :802-806); a bare `hdr_status` field would not compile under the glow feature set unless gated or unless the type is redefined in an egui/eframe-local module. Nothing in §7.4 decides this.
- **Evidence:** plan header ("`egui_glow` does not exist at 0.36"); tag `crates/egui_glow/Cargo.toml` (active, features intact); tag `crates/eframe/Cargo.toml:64-69, :97-101`; tag `crates/eframe/src/native/glow_integration.rs` present.
- **Suggested resolution:** define `HdrStatus`/`SdrReason` in `egui_wgpu`, gate the `IntegrationInfo` field (if kept after finding 2) exactly like `wgpu_render_state`, and re-export from eframe. Add one honest paragraph upstream: wgpu-only in v1, glow parity explicitly out of scope (glow cannot do fp16 surfaces portably anyway) — that defensible scoping does not require the false "glow doesn't exist" premise.

### 4. hdrpreference-variants — `HdrPreference` naming misses egui's own convention and the two variants users will ask for
- **Severity:** major
- **Finding:** (a) `PreferExtendedSrgb` names a *mechanism* (format+color-space combo), contradicting the plan's own §1 argument for policy-not-knobs; the user's intent is "use HDR if available". egui's comparable enum is `ThemePreference` (`egui/src/memory/theme.rs:67` — `Light/Dark/System`), and wgpu's `SurfaceColorSpace::Auto` exists precisely for probe-and-decide; an `Auto` variant is the first thing upstream review will demand (default `Off` means the ecosystem stays SDR forever, one code change per app). (b) Apps that *require* HDR (video scopes: silent SDR fallback corrupts review) get only post-hoc detection via `HdrStatus`; a `Required`-style variant that fails `RenderState::create` is a design question §7.4 leaves open while admitting "richer HdrStatus / new policy variant" growth into PR 2. (c) Mechanical constraint missed: `SurfaceConfig` derives `Clone, Copy, PartialEq, Eq, Hash` (lib.rs:70-71), so `HdrPreference` must be `Copy+Eq+Hash` — any future payload-carrying variant (e.g. `Required { min_headroom: f32 }`) breaks the struct's derives. (d) serde is a non-issue and shouldn't spend issue-text: neither `SurfaceConfig` nor `WgpuConfiguration` derives serde.
- **Evidence:** plan §1 enum sketch; §7.4 PR-2 evolution; tag `crates/egui-wgpu/src/lib.rs:69-71`; tag `crates/egui/src/memory/theme.rs:6, :67`; registry `wgpu-types-30.0.1/src/surface.rs:242+` (`Auto` variant).
- **Suggested resolution:** rename to intent-space: `HdrPreference::{ Off, Auto, ExtendedSrgb }` (unit variants only, preserving `Copy/Eq/Hash`), document `Auto` as the likely future default, and answer the fail-hard question explicitly: either a `Required` variant *or* a documented "check `hdr_status` after create" recipe — pick one in the issue text.

### 5. format-fn-contract — the new `preferred_framebuffer_format` signature: kept name lies, error domain unspecified, tuple return unmerited
- **Severity:** major
- **Finding:** The `caps`-typed parameter is well motivated — wgpu 30 puts HDR-only formats exclusively in `SurfaceCapabilities::format_capabilities`, not `formats` (surface.rs:509-524), so a `&[TextureFormat]` slice cannot even see `Rgba16Float` on such surfaces — but the rest of the sketch is under-defined. (a) The Err case is never stated: today the only error is `NoSurfaceFormatsAvailable` (lib.rs:419-434); does the new function ever fail under `HdrPreference::Off`? Under `PreferExtendedSrgb`? If never, why a tuple-carrying `Result` instead of the status living solely in `RenderState`? (b) Keeping the name while the return grows to `(TextureFormat, HdrStatus)` fails the plan's own anti-drift test — the name says "format"; the function now decides a *surface target*. (c) The plan's semver precedent is partly false: "0.35→0.36: glow removed" — glow was not removed (verified above), and this checkout has no 0.35 tag at all to check the `Renderer::new` claim against; the wgpu 29→30 bump is real (workspace Cargo.toml, 0.34.3 vs 0.36.2). The in-place 0.x break itself is fine and idiomatic for this repo — but the justification should be true.
- **Evidence:** plan §7.4; registry `wgpu-types-30.0.1/src/surface.rs:505-551`; tag `crates/egui-wgpu/src/lib.rs:419-434`; fork tags 0.34.3/0.36.2 Cargo.toml (wgpu 29.0.1 → 30.0, glow present in both).
- **Suggested resolution:** one public function, new name: `decide_surface_target(caps: &SurfaceCapabilities, hdr: HdrPreference) -> Result<SurfaceTarget, WgpuError>` with `SurfaceTarget { format, color_space, status }` (a named struct, not a 3-tuple — `decide_target`'s internal tuple return has the same smell). State the Err condition in one sentence (probably: only `NoSurfaceFormatsAvailable`, unchanged). Cite the real precedent (wgpu major bump in a minor) and drop the glow claim.

### 6. colorspace-projection — `preferred_color_space` symmetry is cosmetic and its totality hides an error
- **Severity:** major
- **Finding:** Color-space support is *per format* in wgpu 30 (`SurfaceFormatCapabilities { format, color_spaces }`, surface.rs:488-503); there is no well-defined "the surface's color space" independent of the chosen format. The proposed `preferred_color_space(caps, hdr) -> SurfaceColorSpace` therefore either re-derives a format internally (duplicating the picker) or assumes one — the "same inputs, never asymmetric parameter lists" argument buys no actual guarantee. And the asymmetric error treatment breaks the claimed symmetry harder: the sibling returns `Err` when `formats` is empty, this one returns `Auto` "if no formats at all" — same broken surface, two different answers. A caller who pairs this function's output with their own format selection can configure `(format_without_extended_srgb, ExtendedSrgb)` and only wgpu validation catches it.
- **Evidence:** plan §7.4 ("New symmetric projection…", "total; `Auto` if no formats at all"); registry `wgpu-types-30.0.1/src/surface.rs:488-503, :538-551`.
- **Suggested resolution:** make it private (or delete it): `configure_surface` should read the stored `color_space` from `RenderState` (which the plan already mandates), and hand-rolled users call the single `decide_surface_target`. If a projection must exist, take the decided format: `preferred_color_space(caps, format) -> SurfaceColorSpaces-or-Auto` and make emptiness explicit.

### 7. output-encoding-stored — threading `OutputEncoding` as a stored field re-introduces the incoherence §7.4 claims to eliminate
- **Severity:** major
- **Finding:** §7.4's design goal is "Coherence is by construction, not discipline … no derivation match anywhere". §2 then adds a *fourth* decision output (`OutputEncoding`) threaded "surface config → RenderState → Renderer::new", stored alongside `target_format` + `target_color_space` — but encoding is a total function of exactly that pair (`*Srgb`-family + `ExtendedSrgb` ⇒ Gamma; float + `ExtendedSrgb` ⇒ Linearize...). Storing a derivable value next to its inputs is the same drift-on-discount the plan just built `decide_target` to kill: one PR later someone updates `target_color_space` without the encoding. Also the naming mixes categories (`Gamma` noun, `Linearize` verb) where egui/wgpu peers use adjectives (`TextureFilter::Linear/Nearest`, `SurfaceColorSpace::ExtendedSrgbLinear`), and placement is unstated: the natural public spot is `RendererOptions` (renderer.rs:175-200), which standalone `Renderer` users — the author's own old hand-rolled loop — construct by hand, so its default needs a defined derivation from `output_color_format`.
- **Evidence:** plan §2 (sketch + threading sentence) vs §7.4 ("no derivation match anywhere"); tag `crates/egui-wgpu/src/renderer.rs:175-200, :407-414`.
- **Suggested resolution:** either `OutputEncoding::of(target_format, target_color_space) -> Self` computed once at `Renderer::new` call time (zero stored state), or make it the fourth `decide_target` output so the invariant unit test covers it. Rename variants `{ GammaEncoded, Linear }` (or `TransferFunction`), and add it to `RendererOptions` with a documented default.

### 8. imagedata-eq-cascade — `ImageData::Float` is not "purely additive": an Eq cascade and an undecided variant shape
- **Severity:** major
- **Finding:** §5 calls tier C "purely additive". It isn't: `ImageData` derives `Clone, PartialEq, Eq` (image.rs:14), `ImageDelta` derives `Clone, PartialEq, Eq` (image.rs:453-456), `TexturesDelta` derives `Clone, Default, PartialEq, Eq` + serde (textures.rs:281-285). Any float pixel type (`[f32;4]` or half's `f16`) has no `Eq`, so all three lose `Eq` — a visible breaking change to anyone with `T: Eq` bounds over these types, and it should be listed in the PR-3 changelog sentence, not discovered by CI. Separately, the variant shape is undecided: the plan says "pixels `Vec<[f32;4]>`" but the existing variant is `Color(Arc<ColorImage>)` — `Float` needs a `FloatImage { size, pixels }` wrapper (an `ImageData` variant with no size can't implement `ImageData::size()`), an `Arc` for cheap cloning parity, an `impl From<FloatImage> for ImageData` (required by `ImageDelta::full/partial(impl Into<ImageData>)`, image.rs:473-492), and the ColorImage-parity helpers (`new`, `filled`, `from_rgba_*`, and a `FloatImage::from_color_image` lossy helper) that the plan never enumerates.
- **Evidence:** plan §5 tier C row ("purely additive"), §7.1 bullet 1; tag `crates/epaint/src/image.rs:14-19, :453-492`; tag `crates/epaint/src/textures.rs:281-285`.
- **Suggested resolution:** spec `Float(Arc<FloatImage>)` with `FloatImage { size: [usize; 2], pixels: Vec<[f32; 4]> }`, list the helper set, and add one sentence to the plan: "tier C removes `Eq` from `ImageData`/`ImageDelta`/`TexturesDelta`".

### 9. float-ram-half — the 16 B/px f32-in-RAM choice ignores that `half` is already in the tree and the upload converts anyway
- **Severity:** minor
- **Finding:** The "no `half` dep" rationale is weaker than stated: `half 2.7.1` is already resolved in this workspace's `Cargo.lock` (line 2206, via wgpu/naga), so adding it to epaint adds a direct dep but no new vendored code; `half` is tiny, `no_std`, and its `serde`/`bytemuck` features are exactly what tier E will need anyway. Meanwhile the plan's own pipeline is RAM-f32 → convert → `Rgba16Float` upload (8 B/px), so RAM-f16 makes storage exactly 1:1 with the upload format and halves the 132 MB a 4K frame costs at 16 B/px (vs 33 MB for `ColorImage`'s 4 B/px — worth stating in the issue so reviewers see the multiplier). `TextureOptions` needs *no* changes (magnification/minification/wrap/mipmap cover it; `Rgba16Float` is filterable), which the plan could say affirmatively instead of leaving "TextureOptions surface area" open — the API-doc items that must change are the Rgba8Unorm-only docs on `register_native_texture` and the hardcoded texture creation (renderer.rs:701-705, :772-824).
- **Evidence:** plan §7.1 bullet 1; `Cargo.lock:2206-2207`; tag `crates/epaint/src/textures.rs:158-181`; tag `crates/egui-wgpu/src/renderer.rs:701-705, :772-824`.
- **Suggested resolution:** decide now (it shapes tier E's dep story): `[f16;4]` in RAM behind the existing `half` dep, or keep f32 for v1 but write the issue sentence "RAM format is deliberately f32; fp16 is an upload detail" so it isn't relitigated in review.

### 10. hdr-picker-hsva — `color_edit_button_hdr(&mut Rgba)` cannot reuse the existing picker pipeline, omits the `Alpha` parameter, and collides with an existing function over the same state type
- **Severity:** major
- **Finding:** (a) Every existing `color_edit_button_*` round-trips through `Hsva` (e.g. `color_edit_button_rgba` at color_picker.rs:565-572) with a `FixedCache<Rgba, Hsva>` (color_picker.rs:585-599). The HSV machinery is documented "All ranges in 0-1" and clamps saturation (hsva.rs:206-218); on premultiplied extended-range input (`hsv_from_rgb` divides by a possibly-negative max; negative channels are *legal* under the §7.1 odd-symmetric contract) hue/sat are garbage, so tier D needs either a new edit model (extended RGB/stops sliders, no HSV) or a defined extended-Hsva — §7.1 says "picker edits `&mut Rgba`" and stops there. (b) The sketch `color_edit_button_hdr(&mut Rgba)` drops the `Alpha` parameter every sibling carries (color_picker.rs:518-575) — an inconsistency reviewers will flag on sight. (c) `color_edit_button_rgba(&mut Rgba, Alpha)` *already exists* (color_picker.rs:565): two public functions taking the identical state type with different range semantics (0-1 vs extended) is a type-system failure the plan should pre-empt — upstream will ask "why not extend the existing one?" and the plan has no answer. (d) `Rgba` is premultiplied (rgba.rs:1-12, "0-1 linear space … with premultiplied alpha"); slider-authoring over premultiplied state misbehaves when alpha < 1 (changing alpha rescales rgb) — the existing widgets un-premultiply for editing (`to_rgba_unmultiplied`, hsva.rs:150-159); whether tier D's edit state is premultiplied or straight is undecided, and "Rgba is unclamped so it's the right edit space" (§5 tier D) silently rewrites `Rgba`'s documented 0-1 contract.
- **Evidence:** plan §5 tier D row, §7.1 derived-API bullets; tag `crates/egui/src/widgets/color_picker.rs:518-599`; tag `crates/ecolor/src/hsva.rs:150-218`; tag `crates/ecolor/src/rgba.rs:1-12`.
- **Suggested resolution:** in the plan, spec tier D as: `color_edit_button_hdr(ui, rgba: &mut Rgba, alpha: Alpha)` (parameter parity), straight (un-premultiplied) slider state converted at the paint boundary, RGB+stops sliders only (explicitly no HSV in v1), and one paragraph on the coexistence rule vs `color_edit_button_rgba`.

### 11. vertex-f16-ripple — tier E's consumer list is wrong in both directions and the type-level ripple is underpriced
- **Severity:** major
- **Finding:** §5's tier E row lists as consumers "the software renderer, kittest snapshot comparison, capture readback, mesh serde" — but epaint has no software renderer at 0.36.2 (no such module in the tag tree), while the *existing* `egui_glow` backend (which unpacks vertices into its own GLSL attributes and its own stride constants) is missing from the list — same stale inventory as the header's glow claim. The type-level ripple the plan underweights: `Vertex` derives `PartialEq, Eq` + serde + `bytemuck::Pod/Zeroable`, in *two* cfg variants including a `unity` variant with reordered fields (mesh.rs:8-24 vs :39-55) — the "adjacent u32 slot" packing trick (§7.6) has to work in both field orders; `Mesh` derives `Eq` (mesh.rs:58-60) and `Shape` contains meshes, so f16 color drops `Eq` through `Vertex → Mesh → Shape`; serde representation of the color field needs a decision (Color32 serializes as a `#rrggbb` string — what does f16x4 serialize as? half's serde feature serializes `f16` as float, but that must be chosen, plus the `half` features become epaint's direct dependency surface); and `Pod` for `[f16;4]` needs half's `bytemuck` feature.
- **Evidence:** plan §5 tier E row, §7.6; tag `crates/epaint/src/mesh.rs:8-24, :39-55, :58-60`; tag `crates/epaint/src/lib.rs` module list (no software renderer); tag `crates/egui_glow/` present.
- **Suggested resolution:** rewrite the tier E consumer list from `git grep` against the real tag (egui-wgpu pipelines, egui_glow GLSL, kittest/capture, Mesh/Shape serde+Eq), and add the three type decisions (Eq removal acknowledged, serde repr, `half` features) to the §7.6 deferral note so the future PR doesn't reopen them cold.

### 12. surfaceconfig-create-only — putting a create-time-only policy inside a struct documented "edit any field to have the surface reconfigured" is a silent-no-op trap
- **Severity:** major
- **Finding:** `SurfaceConfig`'s contract is "Runtime-mutable subset … Edit any field to have the surface reconfigured on the next paint" (lib.rs:69-71), and the mutation flow is real: `Frame::set_wgpu_surface_config` (epi.rs:~815) → per-paint diff in the Painter (winit.rs:526-533). §4 decides HDR should be "create-time-only via `NativeOptions`" with an explicit `Painter::set_hdr()` full-recreate — but §1/§7.4 put `HdrPreference` in `SurfaceConfig`. Result: an app flips `surface_config.hdr_preference = Auto` at runtime, the documented contract promises a reconfigure, and the probe silently ignores it (or worse, half-applies: reconfigure without pipeline rebuild = black screen, the exact #7484 failure §1 cites as motivation). The plan's own two sections disagree on which struct owns the policy.
- **Evidence:** plan §1 ("extend `SurfaceConfig` with an HDR policy"), §4 ("HDR declared create-time-only via `NativeOptions`"), §7.4; tag `crates/egui-wgpu/src/lib.rs:69-71, :332-346`; tag `crates/egui-wgpu/src/winit.rs:526-533`.
- **Suggested resolution:** one decision, one sentence: policy lives in `WgpuSetupCreateNew`/`RendererOptions`-style create-time config (or a dedicated `WgpuConfiguration` field documented create-time-only), `SurfaceConfig` stays runtime-mutable-only, and `set_hdr()` is listed as PR-1 or explicitly deferred with its absence documented.

### 13. pr1-undecided — three admitted-open items are PR-1 blockers, not footnotes
- **Severity:** major
- **Finding:** §7.4 itself defers "which surface's probe decides the global format (primary? any?) — one sentence to pick when writing PR 1", and the headless/no-surface path is unhandled: `RenderState::create` synthesizes `vec![Rgba8Unorm]` when there is no compatible surface (lib.rs:271-277), so there are no caps to probe — the plan doesn't say what `HdrStatus`/`decide_target` return there (`Sdr { reason: NoSurface }`? a new reason?). Between that, the blank `Hdr { .. }` payload (finding 1), and the undefined Err domain of the new format function (finding 5), PR 1's core function cannot be written from the plan as it stands. These are exactly the decisions that should be settled *in the upstream issue text* so review doesn't stall on them.
- **Evidence:** plan §7.4 ("Residual policy footnote…"), plan appendix (`RenderState::create` no-surface fallback); tag `crates/egui-wgpu/src/lib.rs:271-278`.
- **Suggested resolution:** before drafting the issue, write the three sentences: (1) probe policy (primary viewport's surface decides; late viewports inherit), (2) no-surface answer (`HdrPreference` irrelevant → `Sdr { NoSurface }`, or `Off` normalized), (3) Err semantics of the public function. Each is one sentence; all three gate compiling PR 1.

## Verdict
The API skeleton — a policy enum, one internal decider, stored-and-named decision outputs, status-as-enum — is the right shape and better than what egui has today. But the reporting story (§7.4) rests on a "refresh at reconfigure" point that does not exist in the code, `HdrStatus`'s payloads are blank while §1 contradicts §7.4 (`bool` vs enum), and the policy's home (`SurfaceConfig`) contradicts the plan's own create-time-only ruling. Every "purely additive" tier claim hides a real type-level ripple (Eq cascades, feature gating, serde repr) that must be priced into the PR sequence, and the "exactly one backend" premise is false at this tag. Fixable with a focused rewrite of §1/§7.4 plus the thirteen decisions above.
