# Review: Sequencing, scope discipline, app-coverage realism — hdr-egui-upstream.md

Reviewer focus: Is the tier→PR ladder merge-order-safe, is the fork/patch strategy sound, and does the "~all realistic apps" claim survive contact with real app categories?

Checkout facts: HEAD = `47c3d1b71` ("Add egui HDR enablement plan notes"); tag `0.36.2` is **not an ancestor** of HEAD (213 commits in HEAD not in tag, 16 in tag not in HEAD — the plan's 0.36.2 anchors and the working tree have diverged). `crates/egui_glow` exists and is functional at both the tag and HEAD. `hdr-egui-port-plan.md` (the plan's own reference [1]) is absent from the repo. All `file:line` cites below are the working tree unless prefixed `git show 0.36.2:`.

## Findings

### 1. glow-exists — The "egui_glow does not exist / exactly one backend" premise is false, and the omission propagates through every tier
- **Severity:** critical
- **Finding:** The plan's header and sequencing strategy rest on "egui_glow does not exist at 0.36 — wgpu is the only GPU backend, so there is exactly one backend to fix." This is wrong at both refs. `egui_glow` is present at `0.36.2` and at HEAD, and eframe ships a first-class `glow` feature with `NativeOptions::renderer`/`WebOptions::renderer` selection and a *positive* recommendation for binary/wasm size (citing #5889). The `custom_3d_glow` example exists in this repo. Consequences the plan never handles: (a) tier B fixes nothing for glow eframe apps — a documented, size-motivated segment of users; (b) tier E's "ripple through **every** consumer of the mesh" list names a *software renderer that doesn't exist in the repo* (see finding 8) but omits the glow painter that does; (c) §7.4's culture argument cites "0.35→0.36: glow removed" — glow was not removed. A reviewer will ask "what about glow?" in PR 1's first week; the plan has no answer drafted.
- **Evidence:** plan header (lines 1-9) and §7.4; `git show 0.36.2:crates/egui_glow/README.md` ("Render egui using glow on both native and web"); `git show 0.36.2:crates/eframe/Cargo.toml:56-61,84-91` (glow feature, `NativeOptions::renderer`, #5889 size rationale); `git ls-tree 0.36.2 crates/` and `git ls-tree HEAD crates/`.
- **Suggested resolution:** Correct the claim; add an explicit non-goal/limitation line to PR 1 ("glow backend: SDR-only; HDR requires the wgpu painter") and to the issue text. Recompute tier E's consumer list to include `egui_glow/src/painter.rs` or explicitly scope E to the wgpu backend. Drop the "glow removed" citation from the 0.x-breaking-change argument (the wgpu-major-bump and `Renderer::new`→struct examples suffice).

### 2. frame-info-mirage — PR 1 bundles `HdrStatus` reporting into `frame.info()`, an API that doesn't exist, and the plumbing crosses the crate boundary tier B claims not to touch
- **Severity:** major
- **Finding:** PR 1 per §5 includes "HdrStatus reporting (`RenderState` + `frame.info()`)". There is no egui API by that name carrying render info: `eframe::Frame::info()` returns static `IntegrationInfo` (epi.rs:800-803); egui's per-frame output struct `FullOutput` (egui/src/data/output.rs:13-42) flows *egui→backend* only — there is no backend→egui feedback channel, and adding one means editing the `egui` crate, contradicting tier B's "crates touched: `egui-wgpu` only" and the ~150-line budget. Meanwhile `eframe::Frame::wgpu_render_state()` (epi.rs:943) already gives apps read access to `RenderState` today, so the `RenderState` half alone suffices for PR 1 consumers.
- **Evidence:** plan §4, §5 item 1, §7.4, side items ("DisplayHdrInfo pass-through in `frame.info()`"); epi.rs:800-803, 943; output.rs:13-42.
- **Suggested resolution:** Cut `frame.info()` mirroring from PR 1 entirely. Ship HdrStatus as a `RenderState` field only (zero extra plumbing, `wgpu_render_state()` reads it). Move the `DisplayHdrInfo` pass-through to a later PR and acknowledge it needs either mirrored types in `egui` (which cannot depend on wgpu-types) or an eframe-side accessor — a design decision, not a side item.

### 3. runtime-vs-createtime-knob — §1 puts the HDR policy on `SurfaceConfig`, whose documented contract is runtime mutation, while §4 decides HDR is create-time-only; the knob's home decides PR 1's acceptance
- **Severity:** major
- **Finding:** §1: "extend `SurfaceConfig` with an HDR *policy*". But `SurfaceConfig` is documented "Runtime-mutable subset of `WgpuConfiguration`" (egui-wgpu/src/lib.rs:71-72), `Painter::set_surface_config` exists and is "cheap to call every frame" (winit.rs:87-108, reconfiguring *all* surfaces), and eframe exposes a runtime surface-config path to apps. Putting `hdr` on that struct advertises "flip it at runtime and it reconfigures" — exactly the #7484 baked-pipeline invalidation the plan says it cannot cheaply support (§4 decides "create-time-only plus explicit `Painter::set_hdr()`"). §4 also notes pipeline targets are baked per `target_format`, so a runtime flip needs the full context+renderer recreate. This unresolved contradiction is PR 1's most likely review blocker, and it's invisible in the PR-1 bullet list.
- **Evidence:** plan §1 ("extend SurfaceConfig"), §4 (runtime switching decision), §5 item 1; lib.rs:71-72; winit.rs:87-108, 589-592.
- **Suggested resolution:** Decide before drafting: either `HdrPreference` lives on `WgpuConfiguration` (create-time) with `set_hdr()` as the sanctioned runtime path, or it lives on `SurfaceConfig` and PR 1 commits to runtime switching semantics. State the choice as an explicit non-goal sentence in PR 1 ("HDR is create-time-only; runtime changes require recreate via X") — without it, reviewers will assume the `SurfaceConfig` doc applies to the new field.

### 4. kittest-cant-do-hdr — §7.7's "headless offscreen rendering to fp16 works" is unverified and currently false-by-plumbing: kittest creates no surface, so the probe always falls back to Rgba8
- **Severity:** major
- **Finding:** kittest's wgpu renderer is explicitly headless with no display handle (`egui_kittest/src/wgpu.rs:65`: "No display handle needed for headless testing — we don't present to a window"), constructing `WgpuConfiguration { wgpu_setup, ..Default::default() }` with no compatible surface. `RenderState::create` then takes the `map_or_else(|| vec![Rgba8Unorm], …)` default (egui-wgpu/src/lib.rs:273-279), so after PR 1 the CI probe sees `[Rgba8Unorm]` → `Sdr { NoExtendedSrgb }` → Rgba8 target. Result: neither PR 2's encoding/dither behavior nor PR 3's float-texture content is exercisable in snapshot tests at all, and readback is hard-coded `image::RgbaImage` (egui_kittest/src/lib.rs:142). No tier, PR, or side item owns the needed kittest target-format override + fp16 readback.
- **Evidence:** plan §4 ("capture reads back Rgba8"), §5 side items, §7.7; egui_kittest/src/wgpu.rs:63-71; egui-wgpu/src/lib.rs:273-279; egui_kittest/src/lib.rs:138-142.
- **Suggested resolution:** Sequence the kittest work as a hard dependency of PR 3 (and design PR 1 so a target-format override is possible — e.g. honor an explicit format in `WgpuConfiguration`/test setup instead of only the capability probe). Verify §7.7's offscreen-fp16 assumption with a 20-line spike before the upstream issue claims CI-testability.

### 5. coverage-claim — "~all realistic apps" at C+D survives only for bitmap-shaped, sRGB-gamut HDR; two of the five canonical categories break in ways §6 doesn't admit
- **Severity:** major
- **Finding:** Stress-testing the claim: (a) **Wide-gamut photo editor (P3 export)** — §7.2 concedes extended-sRGB clips saturated >1.0 colors, so an editor cannot display or proof the very colors it exports; the ceiling is *gamut*, not float range, and §6's coverage sentence carries none of §7.2's caveat. (b) **Node-based compositor** — needs E by §6's own list (waveform/vectorscope traces, curve-editor strokes, annotation text); calling it "~all realistic apps" while the E list names the compositor's core surfaces is self-contradictory. (c) **HDR video player** — covered at C only with two unadmitted costs: app-side bt.2020→sRGB-ext gamut conversion (§7.2) and a full-frame float texture upload per frame (a 4K `Vec<[f32;4]>` frame is ~33 MB to convert and ~16 MB fp16 to upload at 24-60 fps; §6 only prices the CPU-*rasterizer* escape hatch, not the video-playback one). (d) Medical imaging and (e) game-editor viewports do hold at C+D. The honest statement is "all apps whose HDR content is rectangular and inside the sRGB gamut."
- **Evidence:** plan §5 ("C+D already cover … ~all realistic apps"), §6 items 1-4 and the "Who actually needs E" list, §7.2 ("saturated >1.0 colors clip", "gamut conversion is app territory"), §7.1 float-image decision (f32 in RAM).
- **Suggested resolution:** Rewrite the coverage sentence with its two qualifiers (rectangular content; extended-sRGB gamut with app-side conversion), and move the gamut caveat from §7.2 into the upstream issue's non-goals with the video-player bandwidth note — maintainers will ask about bt.2020 content immediately.

### 6. text-at-d-story — "no clean D-tier story for text at all" overstates: a galley-keyed float-texture label cache is a bounded, additive D-tier mechanism, which weakens the flagship justification for E
- **Severity:** minor
- **Finding:** The nits-readout use case (short label, color changes as headroom ramps) is compatible with D: egui already CPU-rasterizes glyphs into a cached atlas and caches galleys; a `hdr_text()` helper can composite atlas coverage × an HDR color into a small cached float texture per text run (a 200×20 readout is ~16 KB fp16), re-rasterizing only when the string/color/DPI changes. That's the same per-string-change cost model as the existing galley cache, not the per-frame full-CPU-rasterizer §6 prices. §6 even concedes "static HDR label → baked text … it works" two paragraphs before "no clean D-tier story for text at all." What D genuinely can't give text: HDR text inside arbitrary mesh effects and zero-per-widget ergonomics. The conclusion (defer E) still stands — but its strongest motivation should not be a claim the E-review thread can debunk.
- **Evidence:** plan §6 (items 2, "no clean D-tier story", and the escape-hatch paragraph); epaint text machinery exists (crates/epaint/src/text/glyph_atlas.rs, fonts.rs); `FontColorTransferFunction` (crates/epaint/src/image.rs:424-426) shows the per-glyph color pipeline is already extendable.
- **Suggested resolution:** Replace "no clean D-tier story" with the honest version: "no *general* mechanism; per-widget texture caching is viable for short labels." If the demo app needs the nits readout, prototype the D-tier `hdr_text` helper — it either validates the deferral with data or becomes the evidence that E is genuinely needed.

### 7. rotated-quad-claim — §6's "you can't even draw a rotated solid HDR line" at D is factually wrong, and it's the kind of wrong a reviewer uses to discount the whole tier-E case
- **Severity:** minor
- **Finding:** egui's `Image`/`ui.image` supports rotation today (`Image::rotate`, image_options.rotation → `mesh.add_rect_with_uv(rect, uv, tint); mesh.rotate(...)`; egui/src/widgets/image.rs:243-247, 867-880). At tier C a float texture makes that a rotated HDR bar (unantialiased, no joins/caps — the code comment at :869-870 notes PathShape+texture is the missing AA path). The strategic point survives (AA strokes, polylines, per-vertex gradients need E), but the sentence as written is falsifiable in 5 lines of egui.
- **Evidence:** plan §6 item 1; egui/src/widgets/image.rs:243-247, 866-880.
- **Suggested resolution:** Restate as "no *antialiased* rotated geometry, no joins/caps, no polylines" and cite the PathShape-texture TODO. Precision here protects the argument's credibility.

### 8. phantom-software-renderer — Tier E's blast-radius list includes a component that doesn't exist and omits ones that do
- **Severity:** minor
- **Finding:** Tier E: "ripple through **every** consumer of the mesh: egui-wgpu pipelines, the software renderer, kittest snapshot comparison, `capture` readback, mesh serde." There is no software renderer in this repo (no such module in epaint/egui; kittest renders via wgpu with a software-adapter *preference*). Meanwhile the actual mesh consumers not listed: the glow painter (finding 1), `Context::tessellate` users outside backends, and `egui_plot`/`egui_inspection`-style crates reading mesh data. If E's cost model miscounts its consumers, its invasiveness estimate is wrong in both directions.
- **Evidence:** plan §5 tier E row and E description; `grep -r "software"` over crates/epaint and crates/egui (no renderer); egui_kittest/src/wgpu.rs:29-31 (software rasterizer *adapter preference*, not a software renderer).
- **Suggested resolution:** Fix the list: {egui-wgpu pipelines, egui_glow painter (or scope E out), kittest, capture, mesh serde, tessellate consumers}. Delete the phantom entry.

### 9. pr1-budget — "~150 lines, no eframe changes" is true only for §1's minimal version; PR 1 as sequenced in §5 is a different, larger PR
- **Severity:** major
- **Finding:** §1's minimal diff (HdrPreference enum + probe + color-space threading, ~150 lines across lib.rs/winit.rs) is credible — eframe exposure is genuinely free (`NativeOptions::wgpu_options: egui_wgpu::WgpuConfiguration`, epi.rs:378, 491-492). But §5's PR 1 adds: the full §7.4 API (breaking in-place `preferred_framebuffer_format(caps, hdr) -> Result<(TextureFormat, HdrStatus), WgpuError>`, new public `preferred_color_space`, internal `decide_target` + invariant tests), `target_color_space`/`hdr_status` RenderState fields, configure-surface threading, *and* the `frame.info()` mirror (finding 2). Realistic surface for that bundle: egui-wgpu lib.rs + winit.rs + renderer-side docs + unit tests + per-crate CHANGELOG + example, roughly 2-3× the stated budget, with a public-breaking-API review on top. Reviewers budget attention by first impression; "small" framing invites a stalemates when the diff lands big.
- **Evidence:** plan §1 ("~150 lines … scandalously cheap"), §5 item 1, §7.4; epi.rs:378, 491-492; egui-wgpu/src/lib.rs:267-289 (create path), 419-427 (preferred_framebuffer_format).
- **Suggested resolution:** Either scope PR 1 to §1-minimal + `decide_target`/`HdrStatus`-in-RenderState (the frame.info() mirror cut per finding 2) and say "~250-350 lines incl. tests/docs", or split PR 1 into 1a (probe+format+color space) and 1b (status reporting). Re-measure against upstream main, not 0.36.2 (finding 12).

### 10. fork-patch-strategy — The `[patch]`-fork option is presented as derisking but is the riskiest path on the table; the app already has a working tier A workaround, so the fork buys little
- **Severity:** major
- **Finding:** §7.9 floats "build PR 1 against an egui fork now and switch our app to it via `[patch]`." If PR 1 stalls one cycle (egui's review backlog makes this the modal outcome, not the tail risk), the fork must chase: upstream main churn (213 commits here since the tag, 11 in egui-wgpu alone), wgpu major bumps nearly every egui release (the plan itself cites 0.35→0.36's wgpu major bump), review-driven API renames to `HdrPreference`/`decide_target`, and CI. That is the hand-rolled-loop maintenance burden the whole plan exists to eliminate, recreated with less control — while the existing tier A workaround (which the plan says "works fine") keeps functioning untouched. A `[patch]`ed app also can't ship until the fork tracks a tagged release.
- **Evidence:** plan §1 ("This PR alone would have eliminated our entire hand-rolled loop"), §7.9 items 2-3, §7.4 (wgpu major bump cadence); divergence numbers in Checkout facts.
- **Suggested resolution:** Invert the priority: (1) file the upstream issue + draft PR 1 against upstream main *early* — a draft PR is free design review and derisks the API shape better than a private fork; (2) keep the app on its tier A workaround until PR 1 merges into a release; (3) permit the fork only as a local scratch testbed, never as the app's dependency pin. Decide the 0.37-vs-0.38 target *after* the issue gets maintainer response, not before.

### 11. side-items-unowned — The "side items" list carries hard dependencies of tier C and a cross-crate design problem, but is sequenced as an unordered grab bag
- **Severity:** minor
- **Finding:** Of the five side items: "capture fp16 readback" is a *hard prerequisite* for testing PR 3 (snapshots clip >1.0 through the Rgba8 path otherwise — finding 4) and belongs in PR 2/3's critical path, not a side list; "DisplayHdrInfo pass-through in frame.info()" is a cross-crate API design problem (finding 2), not an item; "docs + upstream our test app as an example" is release-blocking for adoption claims. Unowned side items are how review threads die: nobody's PR contains them, so nobody writes them.
- **Evidence:** plan §5 item 5 (side items), §4 (capture), §7.7.
- **Suggested resolution:** Re-sequence: capture/kittest fp16 → with or before PR 3; DisplayHdrInfo → own PR 5 with the egui-core mirror decision made; example+docs → in PR 1 or 3 (maintainers expect an example for a feature like this).

Drafting the issue from stale anchors wastes the one good first impression.
- **Evidence:** plan Appendix ("verified … 0.36.2"); git ancestry check (Checkout facts); lib.rs:267-271 vs plan Appendix "preferred_framebuffer_format … :411-427".
- **Suggested resolution:** Add a pre-drafting workstream: re-verify every Appendix anchor against upstream `main` (not the tag, not this fork) and diff the egui-wgpu API surface for changes since 0.36.2; restate §7.4's signature-change rationale against the current `Result`-returning signature.

### 14. tier-c-additive-caveat — Tier C's "purely additive" claim ignores that `ImageData` is a closed, serde-derived enum
- **Severity:** minor
- **Finding:** Adding a float variant to `ImageData { Color(Arc<ColorImage>) }` breaks every exhaustive match downstream and extends the serde format (epaint/src/image.rs:14-19). egui 0.x culture tolerates this, but PR 3's review will require a changelog breaking-change note and possibly a `non_exhaustive` decision — none of which the "additive, doesn't disturb the SDR path" framing anticipates. Relatedly, PR 4's "unclamped color plumbing" names no concrete functions (which ecolor clamp sites does the picker actually hit? `gamma_u8_from_linear_f32`'s clamp at ecolor:112-124 is only relevant if HDR widgets produce `Color32`s), leaving PR 4's true scope unmeasured.
- **Evidence:** plan §5 tier C ("purely additive"), §5 item 4 ("unclamped color plumbing"); epaint/src/image.rs:14-19; plan Appendix ecolor anchors.
- **Suggested resolution:** In the ladder table, mark C "additive + one breaking enum variant (serde note required)". Enumerate PR 4's exact ecolor touchpoints or drop "unclamped color plumbing" to "none needed — `Rgba` is already unclamped; visuals go through tier C textures."

### 15. pr2-dithering-precedent — PR 2's "auto-disable dithering for float targets" collides with an existing user-facing dithering option the plan never mentions
- **Severity:** minor
- **Finding:** Dithering is already a public three-layer knob: `NativeOptions::dithering` (epi.rs:404, WebOptions:546), `RendererOptions::dithering` with an sRGB-assumption doc (renderer.rs:193-200) plumbed through a shader uniform (renderer.rs:147, 293, 970). PR 2's automatic suppression must define precedence (user `false` = off; user `true` + float target = ?), or it silently overrides an existing option and fails review. Small, but it's in the plan's own PR 2 scope and unaddressed.
- **Evidence:** plan §2 ("auto-disable `dithering` for float targets"), §5 item 2; epi.rs:404, 546; renderer.rs:193-200, 219-232.
- **Suggested resolution:** One sentence in PR 2: dithering is forced off on float targets regardless of `RendererOptions::dithering`, doc updated to say it "assumes an 8-bit sRGB target."

## Verdict
The tier ladder's invasiveness logic is sound and B-first is right, but the sequencing narrative contains two false factual premises (glow removed, `frame.info()` exists) and one internal contradiction (runtime-mutable `SurfaceConfig` vs create-time-only HDR) that would each derail PR 1's review. The unsequenced kittest/fp16 CI dependency means tier C currently has no test story. The `[patch]`-fork option should be demoted in favor of an early draft PR against upstream main, which the plan must first be re-anchored to. "~all realistic apps" needs its two missing qualifiers (rectangular content, extended-sRGB gamut).
